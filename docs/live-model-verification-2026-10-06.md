### P1-1：保留端点的具体错误原因

三个适配器现在保留结构化 `error.message`，限制长度、移除控制字符并脱敏已配置凭据和 Bearer 内容；不透传任意原始响应。HTTP 状态、请求 ID、Retry-After 和上下文超限分类继续保留。45 项 provider 测试通过，新增脱敏与诊断回归先失败再通过。故意构造未完整应答的工具批后，真实端点仍 HTTP 400，适配器现在明确报告 insufficient tool messages，而非通用配置错误。

首次全量回归发现重试模块仍断言结构化 fixture refused 必须被隐藏，与本项修复后的契约不符。独立重跑确认同一断言失败；更新后从真实 HTTP 经 Agent 验证重试次数、rate-limit 分类、结构化原因可见、密钥/Bearer/无关 debug 字段不泄露，重试模块 15 项通过。该补充仅修改回归断言，没有追加运行时代码变更。

P0-3 另外通过真实模型完整 Agent 路径：父模型读取合成文件、调用 `subagent_fork`、子模型继承对话并提交报告，父运行 `completed`。

### P1-3：未执行诊断必须说明检查不完整

无服务器或服务器尚未发布结果时返回 `isError=true`；混合路径保留已有诊断并明确缺失覆盖，空缓存标注为 No cached diagnostics。缺服务器和超时两个真实进程回归先失败再通过；LSP 测试 32 项通过、4 项因未安装实际语言服务器而跳过。真实模型复测实际收到 Diagnostics were not fully checked 与 `isError=true`。

### P2-4：Windows 验证器命令解释器不匹配

真实模型在 host 模式发现并执行 npm:test 成功；Windows 模式失败，原因为 POSIX 单引号进入 cmd.exe，实际程序名成了 `'npm'`，不能笼统归因于 npm 未安装或 host 不解析 .cmd。修复后固定 npm 脚本走 Windows 命令解释器，其他 Windows 验证通过内部原生 argv，避免测试名/路径被 shell 再解释。命令审批仍保留。

回归先复现失败，再检查真实进程写出的临时标记；8 项验证相关测试通过，类型检查通过。真实模型再次发现并执行 Windows npm:test，exitCode=0，打印 SYNTHETIC_VALIDATION_PASS。Node 测试运行器的子进程 EPERM 是另一项环境限制，本修复不承诺解除它。

### P2-6：网络失败缺少底层原因

搜索不可达属于本机网络/服务环境限制，不能靠修改工具消除。但诊断只说 fetch failed 的问题已复现。现在错误保留有界的 cause 链和代码，脱敏搜索凭据并移除控制字符，取消仍按原信号处理；同样适用于 web_fetch。脱敏/原因回归先失败再通过，11 项网页及网络守卫测试通过。真实模型复测得到 fetch failed: [UND_ERR_CONNECT_TIMEOUT] Connect Timeout Error，明确识别连接超时。

### P2-3：未知参数的错误说明

保留严格 schema 拒绝，额外补充允许的顶层参数，不添加未定义的 path 功能。未知参数回归先失败再通过；真实模型再次传入 repo_map.path，被拒绝的结果现在直接列出 query、limit，随后使用正确参数成功。

### P2-10：审批审计区分决策来源

审批结果仍是原有布尔接口，新增可选来源元数据。CLI/Host 分别标记 policy、launch-options、task-approval、user、unavailable；取消继续记录 cancelled，子代理保留来源元数据。没有改变授权优先级或自动放宽权限。预授权写入的真实文件、持久事件和实时事件回归先失败再通过；审批与输入回归 14 项通过，类型检查通过。

### P2-8：Office 表格维度与样本区分

71×4 的真实合成 XLSX 修复前只返回前 30 行 sample，没有完整维度。现在返回完整使用范围 range、其 rows/columns、sample 和 sampleTruncated，使用读取器保留的 fullref，不能把截断后的样本长度冒充总行数。71 行回归先失败再通过；XLSX/Office 工具 3 项在用户会话权限下通过，类型检查通过。真实模型复测明确获得 A1:D71、71 行、4 列和 sampleTruncated=true。

LSP 的 `[5097]` 本身不是错误：同一行已标注 error/severity 和 typescript 来源，它是诊断代码。此部分属于报告对格式的解释，不据此改变诊断含义。

### P2-2：模型可见命令结果区分输出通道

原报告“没有 stdout/stderr”需限定范围：结构化卡片载荷已分流，模型读取的 content JSON 只有 merged output。现在模型文本额外返回 stdout、stderr 的各 6000 字符摘要及 streamsTruncated，保留旧 output 和卡片契约。真实退出/拒绝审批/取消进程回归 3 项通过，类型检查通过。真实模型复测实际收到两条合成输出各自的通道字段，非零退出仍 isError=true。

### P1-4 / P2-11：计划交接的实际问题

原报告“CLI 不提供执行模板”不准确：真实 CLI 原本已打印 plan-execute 的 session、plan 和 hash。但这个模板未保留自定义数据库/工作区；将真实模型刚生成的计划从另一个目录复核，缺路由报 Session not found，指定原库立即成功。

现在交接同时给出 plan-show 和 plan-execute，保留实际数据库与工作区并按 PowerShell/POSIX shell 引号规则输出；submit_plan 结果也携带 session、plan 和 hash。CLI 路由回归先失败再通过，计划相关 25 项通过，类型检查通过。真实模型再次生成计划后，使用打印的 review 命令所带参数从另一个目录成功读回同一计划。

这里验证的是计划路由参数；从任意目录使用 npm run dev 仍需要能定位本项目的 npm 脚本。实际跨目录对照通过已知 CLI 入口启动，再使用打印命令的数据库、工作区与 session 参数；没有执行未经审核的计划。

### P2-5：清单指导语澄清

零进行中并不必然错误：未开始、暂停和已完成的清单都可以没有当前项，现有 API 与回归允许这种状态。旧描述“恰好一个进行中”不适用于这些情况。此次只澄清模型指导语，保留数据接口和状态规则，不把等待中的任务强行变成进行中。todo 原有 7 项通过，4 个整体运行快照通过；快照变更仅为目录描述带来的哈希、字节数及预算估计。真实模型再次提交 completed + pending 后被接受，并说明零进行中合法。

## 性能报告的测量边界

现有性能脚本不能直接证明其部分结论：`firstTokenCount=99` 是计入首个可见文本时间的步骤数，不能用来替代模型请求总数；191 是步骤数，遇到重试时也不等于请求数。脚本输出实际列出 32 个文件末次运行，正文写成 30；自动目标的同文件多轮运行也需要区分。`packages/protocol/statistics.ts` 明确首文本时间包含重试，不计纯工具调用的首文本，不能把差额直接归为排队、网络或隐藏推理。

逐工具脚本跳过每个文件的首次结果，只有 241 条归因样本；累计工具墙钟不是每个并行工具的独立时间，不能用差值精确归因并行调用。原模型耗时分布脚本的去重/取差口径也只得到 27 条非零样本，不能将其当成 191 步的完整分布。应保留原始事件，重新定义请求、步骤、可见文本、重试和工具批的统计口径，再评估性能。

报告表内五个工具耗时相加为 197.5 秒，占其给出的 332.7 秒约 59.4%，并非 95%。表内 `run_command` 中位数是 1077 毫秒，正文的 1 毫秒不一致。没有配对实测之前，不据此修改工具目录、关闭推理、削弱验证、授权或沙箱约束。

本轮同一最小连接提示的请求总耗时分别约 26.1 秒和 6.5 秒（首响应头约 26.1 秒和 6.1 秒），证明单次请求波动，不能证明波动原因。schema 优化前后分别 4/3 轮仅是一个复核对照，不构成稳定提速证据。工具目录字符数不是精确 token 数；等待子代理的 39.6 秒也不能直接归为调度开销。没有进行足够样本的延迟 A/B 测量，本轮结论限于正确性及诊断改善。
