## 4. 新问题 CAP-09：LSP 自定义 command 被继承 package 遮蔽

**级别：P2。状态：真实启动失败及真实配置解析复现，未修改产品实现。**

位置：

- [servers.ts](../packages/lsp/servers.ts) 的 `resolveServers()`：合并内置语言定义与自定义定义时，`package` 默认沿用内置值，约第 179 行。
- 同文件的 `localPackageEntry()` 和 `resolveServerCommand()`：优先按 `package` 找本地 npm 可执行入口；找到后使用它，而不再执行用户显式配置的 `command`，约第 308 行。

**触发条件：** 用户覆盖内置的 `typescript` 等语言，显式设置自己的 command/args；工作区同时安装该语言对应的内置 npm 包；用户没有另外清除继承的 package 字段。

本轮期望启动的是：

```text
node <诊断延迟代理> <真实语言服务器入口>
```

实际解析后却是：

```text
node <真实语言服务器入口> <诊断延迟代理> <真实语言服务器入口>
```

代理未被执行，语言服务器收到错误参数，真实返回：

```text
Language server exited unexpectedly (code 1): error: required option '--stdio' not specified
```

这不是模型未按要求调用工具：模型确实调用了 `lsp_start`，失败发生在配置合并和命令解析。没有本地对应 npm 包时，该覆盖可能正常；安装包以后行为却变化，增加了定位难度。

**本轮配置绕过：** 在临时 `.yuantu/lsp.json` 中显式设置 `package: ""`，使解析器保留所配置 command。之后同一个真实 TypeScript 服务正常启动。另调用冻结源码的实际解析器，比对保留 package 和移除 package 的解析结果，机器证据记录了二者及 `commandShadowed=true`。

**建议：** 当用户显式覆盖 command 且未显式指定 package 时，不应继续隐式继承与旧命令绑定的 package；或者仅在 command 与包提供的命令匹配时启用 npm 入口解析。保留 Windows 本地 npm 入口通过 Node 启动的既有兼容能力。

**验收条件：** 默认配置仍能启动本地包；显式绝对命令、包装器和自定义参数得到保留；包的安装与卸载不会无提示改变显式命令；审批展示的最终命令与实际启动一致。

## 5. 真实任务执行中的优化与限制

S10 的目标只是创建精确内容为 `TASK_OK` 的文件。模型执行了 9 次请求，调用多次 shell 命令：

1. `dir` 检查不存在的目标文件，返回退出码 1；这是预检中的预期不存在情形。
2. 一条命令混用了 Windows shell 和 PowerShell 管道，返回退出码 255，提示 `ForEach-Object` 不是可执行命令。
3. 后续显式命令正确获得哈希、文件大小和字节内容，模型完成文件工具检查与步骤标记。

独立检查确认文件大小 7 字节、内容精确匹配，步骤均为 completed。但运行记录为：

```text
status: needs_review
error: Task side effect outcome unknown; inspect state before retrying.
```

两个失败命令的 effect 仍待复核，所以运行没有自动宣称任务完成。随后本次测试明确调用 `task.verify`，验收通过，任务状态转为 completed，对应 effect 变为 reviewed。

**LIVE-OPT-01：减少简单文件任务对 shell 的依赖。** 优先使用已有列表、读取和交付检查工具；避免用预期非零退出的命令检查文件不存在；确需 PowerShell 时明确 shell 和转义边界。可用同一任务比较请求数、失败命令数和验收状态。

**LIVE-OPT-02：把待复核原因具体呈现给用户。** 如果用户只看到模型“执行完毕”的自然语言，很容易忽略运行状态。界面应显示哪些调用留有未确认 effect、为什么需要验收，以及显式验收后的状态。此项是依据本次真实轨迹提出的优化建议，本轮没有真窗口验证，不能断言当前界面完全缺失这些提示。

保守保留 effect 本身不按缺陷处理。不能因为最终文件正确就自动抹去任意命令可能产生的其他副作用，也不能把显式验收后的完成倒写成运行当时已经自动完成。

## 6. 失败、介入和验收脚本修正

本轮保留以下原始记录，没有删除失败后只保留成功，也没有通过重复相同付费样本来获取绿色结果：

- **历史分页采集参数错误：** S01 和 S03 的模型操作实际完成，证据采集却使用了不支持的分页参数，返回 `Paged history requires an offset`。后续从同一持久数据库读取原结果、执行独立检查，未重复原模型任务。S03 额外执行的是来源恢复后的新阶段。
- **补充脚本布尔配置错误：** 一次补充启动使用 `YUANTU_SUBAGENTS=off`，实际设置表只接受 `0/1/true/false`，Host 在模型调用前拒绝。原启动失败记录保留，脚本改用 `false` 后继续；这不是产品崩溃缺陷。
- **严格只读后端不兼容：** host 不能落实请求的严格只读文件能力，配置被拒绝。随后测试的是独立的会话写入禁用策略，二者没有混算。
- **LSP 缺依赖：** 先记录环境阻塞，再只在临时工作区从 npm 安装 `typescript-language-server@6.0.2` 和 `typescript@5.9.3`，使用独立缓存、关闭安装脚本，没有修改项目的 package.json/lockfile。
- **LSP 配置覆盖失败：** 作为 CAP-09 新问题保留；之后仅在测试配置中清空继承字段，继续诊断场景。不能把绕过后的启动成功描述为产品配置问题已修复。
- **S10 运行状态断言不通过：** 原脚本要求运行直接 completed，实际 needs_review；显式验收后任务才完成，按第 5 节分别记录。
- **S11 附加标记字节断言不通过：** 原脚本要求标记精确无换行，模型实际写入 `CRASH_RECOVERED\n`。提示只要求内容标记，没有明确无换行；因此不能由此推出恢复机制失败。原严格断言失败保留，事务回滚、再次恢复和副作用一次的目标断言分别记为通过。

S11 关键状态：

| 检查点                 | 结果                                                                          |
| ---------------------- | ----------------------------------------------------------------------------- |
| 注入中断事件写入失败后 | run 仍为 running；active_run 仍指向原 run；消息总数与故障前相同；中断事件为 0 |
| 移除故障、再次重启后   | run 为 interrupted；active_run 清空；中断事件恰好 1 条                        |

故障注入只作用于本次测试数据库。终止的 Host 与等待命令均为本次启动的进程，不涉及用户正在使用的桌面或其他测试。
