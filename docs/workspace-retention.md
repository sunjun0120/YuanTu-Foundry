# 工作区保留与清理边界

这份文档回答两个问题：**什么会自己消失，什么永远不会**，以及**一个人该在什么时候决定清理**。它描述的是当前实现，不是建议的长期方向。

## 默认策略：你可能还要的东西不自动删除

格式 4 的未引用快照会按下面的规则自动释放；这里说的是**恢复路径**和**旧格式快照**。没有设置 `YUANTU_WORKSPACE_RETENTION_DAYS` 时：

- **已移除的隔离工作区永远保留。** 目录本身在 `workspace.remove` 时删除，但会话库里的绑定、恢复记录、结果清单和快照引用都保留，`workspace.restore` 可以据此重建。这是默认值，不是遗漏：一个已移除的工作区可能是子代理写下的唯一一份、尚未合入的产物。
- **旧格式快照永远保留。** 早于格式 4、仍带 `refs/yuantu/snapshots/<id>` 的快照不会被自动删除，只能由人看过 `workspace-gc --dry-run` 的报告后决定。
- **Git 对象不会因为一次删除就消失。** 快照元数据和 owner ref 可以立即释放，但对象仍留在仓库对象库里，等待 Git 自己的维护或一次显式的 `git gc --auto`。

## 什么会自动发生

| 时机                                | 自动动作                                                                                                                               |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Host 启动                           | 释放本数据库不再引用的格式 4 快照；清扫被中断的 freeze 留下的 staging；如果配置了保留天数，清除超过天数的已移除工作区                  |
| 删除会话、或归档/移除**工作区**之后 | 本 Host 空闲且没有其他活动 Host 时，再释放一次不再被引用的快照（`releaseSnapshotsIfIdle`）；`session.archive` 只改归档标志，不触发释放 |
| 最后一个引用方释放                  | 删除快照元数据和最后一个 owner ref；对象交给 Git 维护                                                                                  |
| 运行中的按需清理                    | 只有显式的 `workspace-gc`；Host 运行时它拒绝执行                                                                                       |

**不会自动发生**：Git 对象回收（要等 `workspace-gc` 的 `git gc --auto` 或 Git 自己的维护）、已移除工作区的清除（要等保留天数 + 下次 Host 启动）、旧格式快照的删除（永远要人决定）。

## 什么时候该判断“可以清了”

下面这些是信号，不是阈值。出现其中一项时，先看报告，再决定：

- 磁盘剩余空间开始影响其他工作，或备份/升级因为工作区体积变慢；
- `.git` 目录明显大于源码本身，且最近的委派批次已经结束；
- “保留的工作区”里有一批已移除、已经确认不再需要恢复的目录；
- 模型替换、Host 升级或机器迁移之前，希望把不会被带走的字节先处理掉；
- `workspace-gc --dry-run` 的 `needsDecision` 列出了旧格式快照，且你确认其中没有还要恢复的内容。

反过来，**不要在每次运行后清理**：快照和已移除工作区正是失败后恢复、导入未合入成果、审计一次委派的依据。默认保留不是浪费，直到它开始挤占磁盘。

## 怎么清

### 1. 快照与 Git 对象

先关闭使用这个工作区的 Host/CLI，然后：

```powershell
# 只看：快照目录、大小、引用方、需要人工决定的旧快照、staging
node dist/apps/cli/main.js workspace-gc --db <sessions.sqlite> --workspace <项目目录> --dry-run

# 真正执行：释放本库不再引用的快照、清扫 staging，并运行一次 git gc --auto
node dist/apps/cli/main.js workspace-gc --db <sessions.sqlite> --workspace <项目目录>
```

看报告时重点看：

- `snapshots[].bytes`：元数据目录的大小；格式 4 的源码字节在 Git 对象库里，所以这个数**不是**快照占的全部磁盘；
- `snapshots[].owners` / `recordedHere`：还有谁在用；有 owner 的快照不会被删；
- `needsDecision`：旧格式或没有 owner 的快照，**工具不会替你决定**；
- `staging`：被中断的 freeze 留下的临时目录，可以直接清。

`workspace-gc` 只处理当前数据库和当前仓库；同一仓库的其他会话库、其他 Host 的引用会阻止删除。运行中的 Host 会让它直接拒绝，这是为了避免释放与委派并发。

### 2. 已移除的工作区

`workspace-gc` **不会**清除已移除的工作区记录；这条路径只有保留策略：

1. 确认这些目录已经不需要 `workspace.restore`；
2. 设置 `YUANTU_WORKSPACE_RETENTION_DAYS`（1–3650）；
3. 重启 Host。超过天数的记录会在启动时的 housekeeping 中彻底清除，不可再恢复。

保留天数是“从移除时算起”，不是“从最后一次打开算起”。没有立即 purge 的桌面或 CLI 入口；如果必须马上删除，当前实现没有安全的绕过方式，先按保留天数规划，或保留现场等待下一次启动。

### 3. 旧格式快照

`workspace-gc --dry-run` 会把它们标成 `needsDecision`。确认不再需要后，按报告里的快照 id 手工处理；工具不会自动删除它们。

## 边界

- `git gc --auto` 可能因为 Git 自己的宽限期暂不回收刚失去引用的对象；报告里的 `gc` 字段只说明命令是否成功，不承诺字节立即下降。
- 数据库文件移动后，旧路径的 owner ref 会留下，只多占空间，不会误删正在使用的快照。
- 删除快照或清除已移除工作区都不可恢复；恢复记录被清除后，`workspace.restore` 不再有目标。
- 多个 Host 同时存活（模型替换期间）时，运行期释放会跳过，留给下一次空闲或启动。

## 建议节奏

- **平时**：不清理，保留默认。
- **每月或每次大模型替换后**：跑一次 `workspace-gc --dry-run`，只看报告；有 `staging` 或明显不再引用的快照再执行。
- **磁盘紧张/迁移前**：先跑报告，再执行一次 `workspace-gc`；已移除工作区按保留天数处理，旧格式快照逐个人工决定。
