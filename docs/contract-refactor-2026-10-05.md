# DEV-18：计划审批与工具生命周期契约拆分

日期：2026-10-05。依据：[开发建议 DEV-18](development-recommendations-2026-10-05.md)。

## 本批范围与设计

本批限定 Agent 的计划审批 → 工具扩展生命周期 → SQLite 计划持久化这条依赖链。保持工具名称、参数、输出、审批记录、事件和数据库 schema 不变；补强问题通道迟到回复的取消检查。公共契约只依赖 protocol 与 Node 基础能力；core 负责轮次和授权切换，tools 负责派发与 Hook 生命周期，storage 负责持久化。

- 计划正文校验、哈希和存储接口进入 `packages/protocol/plans.ts`。审批组件只要求提交/批准两种操作。
- SQLite 计划 SQL 和状态转换进入 `packages/storage/plans.ts`，SessionStore 保留原方法并委托。新组件接受已有数据库连接及会话存在性检查，连接与事务仍归 SessionStore 管理。
- Agent 中计划工具进入 `packages/core/plan-tools.ts`。批准结果只能由 Agent 在下一轮消费，工具不能直接修改 readOnly 或启动执行。
- Hook 类型进入 `packages/protocol/tool-hooks.ts`，实现进入 `packages/tools/hooks.ts`。注册表继续导出原 API，生命周期实现不依赖 Ajv、工具 SDK 或注册表。
- 工具管线类型、权限视图、延期审批错误和租约续期约定进入 protocol；原入口重导出同一实现，保留异常和类身份。

这批不会同时拆完 Agent/SQLite 的任务、子代理、消息日志、迁移和上下文子系统，也不改 renderer 或新增执行 backend。后续按同样方式逐条依赖链迁移。

## 审查重点

1. 旧入口与新入口的 Error/HookRegistry 身份一致，instanceof 和共享生命周期不漂移。
2. readOnly 只能在轮次边界改变；问题拒绝和取消不能生成已批准计划。
3. 仓储不能绕过会话存在性、跨会话归属、计划状态和哈希见证校验。
4. 不创建/关闭第二个数据库连接，不改变事务、迁移顺序、schema 与历史持久格式。
5. 新 protocol 不反向导入 core/tools/storage；独立组件可在不加载 Agent/完整 SQLite/工具注册表时测试。

## 执行与验证记录

### 职责与依赖变化

- `Agent` 不再直接运行时导入 `storage/sqlite.ts`；计划校验、哈希及租约常量改从 protocol 获取。计划工具只需要 `PlanApprovalStore` 的两种操作，可用小型替身独立测试；Agent 仍负责下一轮重建工具目录、提示词及子代理权限。
- `ToolRegistry` 不再导入 core 的权限实现或延期审批错误；公共权限视图与错误由 protocol 提供。独立 `HookRegistry` 只依赖协议和派发组件；注册表仍保留共享 Hook 的所有者管理。
- `SessionStore` 与 `SqlitePlanStore` 都实现 `PlanRepository`。前者保留原 API，后者封装计划 SQL、状态转换和行转换；借用同一数据库连接，schema 版本仍为 **23**，迁移、事务和连接关闭职责不变。
- HookRegistry、DeferredApprovalError、计划哈希/校验函数和管线常量的旧入口重导出同一对象。新增构建依赖图测试验证独立组件不会加载 Agent、完整 SQLite 或注册表；静态测试也检查公共契约的 type-only import，禁止反向依赖实现包。

### 有意强化的取消边界

`exit_plan_mode` 等待问题通道返回后再次检查 AbortSignal，防止不遵守取消约定的问题通道迟到返回批准时，仍提交并批准计划。这是本批唯一有意改变的行为；拒绝、未回答、超长计划和正常批准的结果保持。迟到回复回归目前在独立 PlanningTools 层验证；原 CLI/Host 计划模式测试继续验证实际入口与下一轮权限切换。

### 后续拆分边界

DEV-18 第一批限定本链，整体条目仍需分批推进。Agent 仍通过类型依赖完整 SessionStore，并负责任务、子代理与上下文；SQLite 仍依赖 core 的任务规范、触发器和脱敏逻辑。下一批优先将任务正文/触发器校验提为公共契约，再单独拆任务仓储；之后分别处理消息日志/迁移与运行协调。每批复用现有行为基线，不把这些未完成边界记为已解耦。
