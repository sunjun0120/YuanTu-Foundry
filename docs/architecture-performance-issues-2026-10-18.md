## 2. 架构现状与约束

### 2.1 运行链路

```text
Electron 渲染层
    ↓ 受校验的命令 / 快照与增量事件
桌面主进程 → CarrierService → AgentHostClient
                                  ↓ JSONL / 子进程或连接传输
                              Agent Host
                                  ↓ 装配与调度
                              Agent 内核
                           ↙       ↓       ↘
                         模型     工具     SQLite 事件日志与投影
```

桌面是当前主要产品入口；CLI 等源码或维护路径的存在不等于对外产品入口全部启用。核心装配位置见 [runtime.ts](../apps/shared/runtime.ts)，包分层规则见 [check-layers.mjs](../scripts/check-layers.mjs)。

最新一次检查结果：18 个包、11 层、4 个应用目录、2 层应用依赖、637 条受分层约束的导入；406 个文件、1,001 条静态值导入边、0 环。环检查排除了 710 条纯类型导入，并提示 10 条动态导入未纳入环检测；不能将结果扩展为所有动态运行路径的无环证明。

### 2.2 需要保留的设计

- 事件日志、会话游标和投影恢复机制，应继续作为状态一致性的基础。
- Carrier 不依赖 Electron 或 DOM，桌面外壳与运行内核有明确接缝。
- 包依赖方向由门禁约束，不能只靠约定维护。
- 流式文本、统计增量和桌面快照差量已存在，优化应延续这些机制。
- 权限按会话保存、待审批调用重新检查策略、默认拒绝等边界，不应为性能优化而削弱。

### 2.3 架构成本

| 约束                                     | 影响                                           | 处理原则                                                       |
| ---------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------- |
| Host 同时负责流式转发、调度与同步 SQLite | 大扫描、序列化或长写事务会占用同一事件循环     | 优先消除重复工作、缩小事务和查询范围；再依据测量考虑工作线程   |
| 单 npm 包、跨逻辑包使用相对导入          | 独立裁剪、版本化和迁移进程边界有成本           | 当前先维持分层门禁，不为拆包而拆包                             |
| 源码 `.ts` 与分发产物并存                | 子程序、脚本资产、原生依赖在打包时需要准确定位 | Host bundle 必须覆盖实际运行路径，不能以 `--help` 成功代替验收 |

当前证据支持继续优化现有架构，未形成必须整体重写的依据。

### R-01：恢复事务吞掉异常，留下部分提交

**位置**：[session-runs.ts](../packages/storage/session-runs.ts) 的 `reconcileInterruptedRuns`、`settleAbandonedRun`；[session-event-journal.ts](../packages/storage/session-event-journal.ts) 的 `transaction`。

**根因**：一个外层事务包住多个会话的恢复，循环内部捕获单会话异常后继续。事务中的嵌套调用直接加入现有事务，没有独立回滚边界。提前完成可能抛错的读取，只能减少部分触发条件，不能使后续多个写入天然原子化。

**故障注入结果**：在临时数据库中创建两个会话与在跑 run，将 owner 改成不存在的进程，使用 SQLite trigger 让其中一个会话的 `run.interrupted` 插入失败。`reconcileInterruptedRuns()` 返回成功恢复 1 个会话，但失败会话已经出现：

```json
{
  "activeRun": null,
  "runStatus": "interrupted",
  "lease": null,
  "interruptedEvents": 0
}
```

这是实际部分提交，不只是“可能有异常”的静态推断。注入模拟的是中途写入失败，不代表已经证明所有 SQLite 故障都具有完全相同的结果。

**影响**：运行状态、租约和作为真源的事件日志不一致；再次恢复可能因 `active_run` 已清空而不再补齐缺失事实。

**建议**：每个会话独立事务，或实现完整 SAVEPOINT；异常时同时回滚该会话的数据库写入、待提交日志和派生缓存。健康会话应仍能恢复，失败会话应保留可重试的一致状态。

**验收**：分别在补未决工具结果、更新 run、清 active_run、删 lease、写中断事件处注入失败；验证失败会话全回滚、健康会话正常恢复、重新打开数据库后结果一致，且重试不重复写入工具结果或中断事件。

### R-02：worktree 快照成本随整树大小增长

**位置**：[snapshot.ts](../packages/workspaces/snapshot.ts) 的 `collectWorkingTree`、`freezeSnapshot`、`buildTree`、manifest 读写；[manager.ts](../packages/workspaces/manager.ts) 的 `fillWorktree`。

**当前行为**：逐文件读取并将内容编码为 base64 存入 manifest；在读取全树、构造摘要之后才检查是否已有已发布快照；子工作树还要从快照写回完整文件集。

**已有缓解**：总输入字节预算已加入，默认 512 MiB，在读取超预算文件前拒绝；对应定向测试已通过。manifest 发布也已有分块写入。这些措施分别约束输入和降低大字符串成本，但没有消除整树 base64 驻留。

**本机夹具**：16 个文件、总计 32 MiB，base64 字符约 42.7 MiB；两次 `collectWorkingTree` 分别约 375ms / 390ms；进程 RSS 从约 74 MiB 到 168 MiB，峰值约 184 MiB。RSS 包含 Node、临时 Buffer 和重复读取，不能把 184 MiB 全部归给单份快照，也不能直接线性推算更大仓库峰值。

**建议**：内容与 manifest 分离，manifest 保存内容标识和元数据；流式读取、哈希与发布；使用可靠指纹避免不必要的重新读取；子工作树按已验证基线减少重复落盘。缓存命中仍必须证明内容未变化，不能仅凭路径、文件数或 HEAD 复用。

**验收**：覆盖未提交修改、未跟踪文件、变化检测、取消与失败清理；在多个仓库大小及多个子代理数量下分别测峰值 RSS、首次冻结、重复冻结和落盘耗时，保留用户 index/HEAD 不变的约束。

### R-03：命令结束统一刷新多个不相关视图

**位置**：[service.ts](../packages/carrier/service.ts) 的 `dispatch`、`refresh`、`refreshTasks`。

**当前行为**：经过主分支的命令结束时仍统一调用 `refresh()`，串行更新会话列表、文件变化、审计、任务历史与后台面板。不是所有命令都走该路径：搜索与部分后台操作已有专门分支。

**已有缓解**：桌面快照按 section 差量发送；会话视图按 revision 复用；支持 `task.history` 时任务历史聚合为单次 RPC；审计已改为按游标增量读取。因此不能再称为“每次都重新传整段对话、重读全部审计或必然 1+2N 次任务 RPC”。

**影响**：一次局部操作仍等待不相关查询；任务历史与变化列表较大时放大延迟。审批等动作还可能触发事件驱动刷新，与命令尾部刷新重叠。

**建议**：声明命令影响的视图集合，合并事件与命令触发的刷新；只更新对应 section。无相互依赖的只读请求可受控并发，同时保留会话切换与版本检查。

**验收**：为审批、回答、取消、重命名、任务更新记录 RPC 方法与次数；局部动作不读取无关历史；验证切换会话、并发刷新及 Host 恢复后不会发布旧会话数据。

### R-04：后台状态读取重复折叠完整日志

**位置**：[params.ts](../apps/agent-host/params.ts) 的 `durableBackground`；[command-jobs.ts](../packages/core/command-jobs.ts) 的 `commandRecords`；[background.ts](../apps/agent-host/handlers/background.ts) 的读取处理器。

**当前行为**：读取隐藏状态时遍历会话事件，再通过 `commandRecords` 遍历日志构造全部命令记录，之后才按 id 或隐藏状态过滤。部分后台状态计算还涉及其他日志折叠。

**已有缓解**：[background-panel.ts](../packages/carrier/background-panel.ts) 已减少逐 job poll、对未变化状态去重，并在空闲时停止轮询。剩余问题主要在 Host 每次读取的成本，不能继续套用旧报告的每秒固定 RPC 数量推算。

**建议**：以 seq 为检查点维护命令与隐藏状态投影；查询单个 job 时避免先重建所有命令；返回历史时增加明确的分页或窗口。保留重启后仍可读取已完成作业的能力。

**验收**：冷启动与热读分别比较折叠事件数；覆盖多会话、隐藏记录、输出游标、重启与丢失生产进程；不能用“只返回活跃命令”牺牲历史输出恢复。

### R-05：Host 启动受到静态导入链影响

**位置**：[tools.ts](../packages/office/tools.ts)、[document.ts](../packages/office/document.ts)、[presentation.ts](../packages/office/presentation.ts)、[catalog/index.ts](../packages/catalog/index.ts)、[build-desktop.mjs](../scripts/build-desktop.mjs)。

**当前行为**：Host 装配工具目录时静态加载 Office 及其较重依赖，即使当前任务不使用 Office。桌面已有 bundle 流程，但不能将它等同于 Host 已完成 bundle。

**本机探针**：源码 `apps/agent-host/main.ts --help` 三次约 3488 / 3521 / 3806ms；单独导入 Office 工具约 1537ms，导入 catalog 约 3446ms。均包含子进程启动与当时机器负载，仅证明模块加载成本；不是 Electron 首屏、真实握手或用户可交互时间。旧报告的不同时间测量不能直接与此相减，认定代码回退或优化比例。

**建议**：Office 实现按需导入；将只用于 schema 的常量与重实现分离；再试验 Host bundle，并验证动态子程序、原生模块、沙箱脚本、worker 与搜索资产的路径。

**验收**：分别测冷/热模块加载、Host 握手、桌面可交互时间；验证 Office、PTY、搜索、程序执行、升级与打包后路径。实验 bundle 的 `--help` 成功不能直接视为可发布。

### R-06：输入和长文本渲染仍有重复工作

**位置**：[renderer-commands.ts](../apps/desktop/renderer-commands.ts) 的 `onInput`；[renderer.ts](../apps/desktop/renderer.ts) 的 `render`；[renderer-live.ts](../apps/desktop/renderer-live.ts) 的流式绘制。

**当前行为**：输入时请求全窗 render；流式文本按约 100ms 合并绘制，但仍重新解析当前预览 Markdown 并替换内容节点。原始文本预览已有尾部长度限制，不能描述为毫无限制增长。

**更正**：[i18n.ts](../apps/desktop/i18n.ts) 的 MutationObserver 按新增节点和变化目标翻译；初始设置语言时存在整文档遍历。现有证据不支持“每次输入都由 i18n 无条件重扫全文档”。

**建议**：输入仅更新命令候选、编辑器与发送状态；流式内容按稳定块复用，控制解析和 DOM 替换范围；保留代码块、折叠推理、滚动位置及输入法语义。

**验收**：用真实桌面录制长会话、长回答、代码块及中文输入法场景，比较输入延迟、长任务、渲染 CPU 和滚动稳定性。当前仅源码确认重复工作，尚未复现具体掉帧率或输入延迟。

## 7. 建议执行顺序与交接要求

1. **先处理 R-01**：建立会话级原子恢复与故障注入回归，避免后续性能改动掩盖一致性缺陷。
2. **处理 R-03 / R-04**：按操作收窄刷新，建立后台增量投影。记录 RPC 次数、扫描事件数与延迟，避免只测空会话。
3. **处理 R-02**：在保持工作树字节、用户 index、凭据排除、取消清理等语义的前提下降低峰值内存和重复 I/O。
4. **处理 R-05**：按需导入后验证 Host bundle；先验收真实工具路径，再比较启动指标。
5. **测量并处理 R-06**：先取得桌面性能录制，之后再调整输入与 Markdown 渲染。
6. **复核原 P3 与打包候选**：按第 6 节逐项确认有效性，形成独立小改动，不批量照抄历史建议。
7. **完成综合验收**：在明确的提交或工作树快照上执行全量检查、桌面冒烟及必要覆盖率；Windows/macOS 和真实模型评测分别记录。

每项交接至少记录：修改前触发条件、根因、涉及路径、回归用例、实际命令与结果、性能夹具规模、仍未验证的平台和场景。不要把定向通过写成全量通过，也不要覆盖或回滚其他会话的未提交改动。

停止与阻塞条件：出现日志/表不一致、用户 index/HEAD 被改动、权限边界变化、夹具无法隔离或测试结果依赖未确认环境能力时，先保留证据并定位原因。不得通过关闭一致性校验、跳过失败测试或放宽权限来制造通过结果。
