## 2. 已做的修复

### 2.1 取消语义的过时断言（缺陷 #6）

诊断输出（临时加、跑完即删）证明产品行为正确：

```
DIAGNOSTIC completion  runs=["completed"] cancellation=null failureClass=null
DIAGNOSTIC cancellation runs=["cancelled"] cancellation={"acknowledged":true,"runSlotReleased":true,"terminalSettled":true} failureClass=null
```

`tests/coding-evaluation.test.ts` 改为断言"取消不得报告已完成的 run"（`runs.every(status === 'cancelled')`），保留 completed/failed 一律拒绝的防护力；`benchmarks/coding-evaluation/{adapters,metrics}.mjs` 的注释改为描述两种真实形态（run 内 abort → `cancelled` RunResult；准入前 abort → `run.start` 拒绝）。RED→GREEN：`21 pass / 1 fail` → `22 pass / 0 fail`。

### 2.2 快照基线重生成 + compaction 夹具预算（缺陷 #1–4）

- 根因一：`packages/core/agent-notices.ts`（并发工作线）给系统提示词新增 767 字符 → 三个场景 `system.chars` 漂移，并连锁改变 `cacheKey`、`inputTokens`、`breakdown`。
- 根因二：`tests/turn-snapshot.test.ts` 的 compaction 场景把自己的余量写明就是留给"系统提示词/工具描述增长"的；767 字符吃掉了余量，场景变为"compaction 不可能"，以 `limited` 结束、0 次请求。
- 修复：`maxContextChars` 21 000 → 22 000（注释说明这次增长与余量），随后执行 `npm run snapshot:update` 重生成 4 个基线。
- 审阅证据（重生成前后逐字段对比，按事件类型对齐而非数组下标）：
  - 4 个场景**请求次数不变**（1 / 3 / 2 / 3），工具指纹**完全未变** → 运行形状没有变化；
  - 差异全部落在：`system.text/chars/digest`（新提示词 767 字符）、由其派生的 `cacheKey`/`inputTokens`/`rawInputTokens`/`windowRoom`/`breakdown.*`、新增计时字段 `firstResponseMs`/`firstTextMs`/`preparationMs`，以及每个请求**新增一条 `statistics.updated`**（同一工作线的进度统计改动）；
  - 唯一的 1 单位差异 `breakdown.tools: 13680 → 13679` 是估算器在 system/tools 之间的取整分摊（工具指纹未变），不是工具变化。

### 2.3 长跑用例改为"每轮都有新证据"（缺陷 #7）

`tests/failure-codes.test.ts:270`：300 轮完全相同 `list_files` 的写法与新收敛规则冲突。改为每轮先把 `progress.txt` 写成新内容再 `read_file`（与并发工作线在 `tests/core.test.ts` 里采用的同一模式），断言保持不变（`round === 301`、`status === 'completed'`），标题与注释说明"有新证据时没有轮数上限"。RED→GREEN：`16 pass / 1 fail` → `17 pass / 0 fail`。

### 2.4 隔离 harness 的进程归属窗口（缺陷 #8，真实缺陷）

`scripts/test-isolation/processes.mjs` 的 `settleProcesses` 用 `creationTime ∈ [started, at]` 证明子进程归属，其中 `at` 是 `spawn()` **返回**的时刻。Windows 上 `spawn()` 在进程创建之前就返回，实测 8/8：

```
window=[...876, ...883] (7ms) created=...886 deltaAfterAt=3ms -> UNVERIFIED
window=[...822, ...827] (5ms) created=...832 deltaAfterAt=5ms -> UNVERIFIED
```

于是自家子进程被判为"非我方"：文件清理 `clean:false` → 调度器置 `unsafe` → **中止整轮剩余文件**（上一轮只跑完 38/249）。修复：给归属证明加上有文档的创建宽限 `CREATION_GRACE_MS = 2000`（保留"pid 复用必定更晚创建"的语义）。RED→GREEN：`tests/test-isolation.test.ts` `18 pass / 1 fail`（且报告进程清理失败）→ `19 pass / 0 fail`，运行后无遗留进程。
