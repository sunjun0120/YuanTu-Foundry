# 内置代码分析服务接入设计

## 背景与目标

Agent 是通用编程 Agent，同时内置源码审计/合规分析能力。用户不提供分析对象、也不调用分析服务时，它的行为和工具面与通用 Agent 完全一致。用户添加源码包、给出 GitHub 仓库或提出分析要求时，它按需加载分析服务工具，对目标做检查分析（SBOM、许可证、漏洞、可维护性等），并输出报告。分析能力由后端团队以远程 MCP 服务（HTTP）提供，按模块划分工具。目标：用户安装后无需任何配置即可调用这些能力，且分析能力的存在不改变通用使用方式。

已确认的前提：

- 后端是远程 HTTP MCP 服务。
- 本地源码包走后端单独的 HTTP 上传接口；GitHub 仓库由后端自行拉取。
- 分两阶段交付：第一阶段不做登录，后端也不鉴权用户，先跑通整体流程；第二阶段再加用户登录与后端鉴权（见第 9 节）。
- 后端工具同步、异步两种都有。
- 后端产出标准报告，agent 在此基础上做定制化解读报告。

现有 MCP 实现只读取工作区的 `.yuantu/mcp.json`，以 `mcp_<id>_list_tools` / `mcp_<id>_call_tool` 两跳代理调用，每次调用按 `external` 审批，调用超时固定 30 秒。这些都不适合内置可信服务，因此采用「把内置服务的工具注册为原生工具」的方案。

## 不在范围内

- 用户登录与后端鉴权（第二阶段，第 9 节只记录预留方案）。
- 把不可信仓库直接作为工作区打开时的整体隔离（不加载其 `AGENTS.md`、Skills、扩展与 MCP 配置）。分析不需要这样打开，推荐路径见第 5 节「分析对象的信任边界」；整体隔离影响面大，单独设计。
- 私有 GitHub 仓库授权。
- MCP 原生 Tasks 机制（作为后续升级路径）。

## 1. 结构与配置

新增 `packages/builtin-services`，分层位于 `packages/mcp` 之上、`packages/catalog` 之下，复用 `packages/mcp` 的连接、HTTP/SSE 传输与输出截断。新包需登记到 `scripts/check-layers.mjs` 的 `LAYERS`。

**内置清单**：构建时生成 `build/builtin-services.json`，随安装包分发，并像 search-assets 一样在 lock 文件中记录 SHA-256、加载时校验。每个服务包含：

| 字段            | 说明                                               |
| --------------- | -------------------------------------------------- |
| `id`            | 服务 ID，使用保留前缀，工作区 MCP 配置中同名即拒绝 |
| `url`           | MCP 端点，必须 HTTPS                               |
| `uploadUrl`     | 源码上传接口                                       |
| `toolPrefix`    | 注册到 agent 的工具名前缀，如 `scan`               |
| `callTimeoutMs` | 同步工具调用超时，默认 300000                      |
| `taskTools`     | 异步任务的状态、结果、取消三个后端工具名           |
| `maxTools`      | 注册工具数上限，默认 64                            |

开发构建可用 `YUANTU_BUILTIN_SERVICES_URL` 覆盖地址（允许回环 http）；正式安装包忽略该变量。工作区 `.yuantu/mcp.json` 不能新增、覆盖或禁用内置服务。

**请求入口唯一**：发往内置服务的所有请求（MCP 传输、源码上传、报告下载）都经同一个请求构造函数生成请求头与选项。第一阶段不带任何鉴权头；第二阶段只在这里加入令牌，其他代码不变。

**生命周期**：沿用 `packages/catalog/resource-pool.ts` 的会话级资源池，同一会话多次运行复用连接，空闲回收。

## 2. 工具注册与权限

- 连接后调用 `tools/list`，每个后端工具注册为 `<toolPrefix>_<后端工具名>` 原生工具，`inputSchema` 原样使用，发送前用 ajv 本地校验。
- 名称非法或过长、schema 超限的工具跳过并记日志；超过 `maxTools` 的部分不注册。
- 权限依据 MCP 工具注解：`readOnlyHint: true` 不声明权限（免审批、可与其他只读工具并行）；其余按 `external` 审批。
- 全部内置服务工具放入延迟加载组「代码分析服务」，经 `load_tools` 按需加载。
- 最近一次成功的工具列表缓存在用户目录；启动时先按缓存注册，后台刷新。`notifications/tools/list_changed` 在下一次运行生效，不改变进行中运行的工具集。
- 断网或后端不可用时，工具保持注册，调用返回明确错误，不让工具消失。

## 3. 代码输入

**原生工具 `analysis_upload_source`**（`external` 审批）：

- 参数为工作区内文件或目录路径，或用户经桌面入口登记的分析对象路径（见第 5 节）。`.zip`、`.tar.gz`、`.tgz` 文件原样上传，不在本地解压。
- 目录在本地打成 zip：复用文件工具的凭据排除规则，并排除 `.git` 与依赖目录；打包清单（文件数、总大小）写入审批描述。
- 以 multipart 调用清单中的 `uploadUrl`，返回 `project_id` 供后续分析工具使用。
- 大小以后端声明上限为准，超出在本地拒绝；报告上传进度，支持取消（中止请求）。

**桌面入口**：输入框增加「添加源码包或文件夹」，只把路径交给 agent，不读取内容进对话。

**GitHub**：由后端拉取工具（第 2 节自动注册）接收仓库 URL 与可选 ref。agent 本地只接受 `https://github.com/<owner>/<repo>` 形式，拒绝其他主机，避免把内网地址交给后端访问。

## 4. 异步任务、结果与报告

**异步任务**：慢工具立即返回 `{ task_id, status }`。agent 把它登记为新的作业类型 `analysis`，作为 `packages/tools/jobs.ts` 作业控制面的生产者：

- `job_list` 列出分析任务与状态。
- `job_output` 调用状态工具，支持等待，等待期间按递增间隔轮询；完成后调用结果工具取回结果。
- `job_kill` 调用取消工具，幂等。
- 任务 ID 写入会话日志，Host 重启后可从日志找回并继续查询。

**大结果**：超过输出预算的结果复用现有溢出落盘，模型拿到摘要与路径，按需 `read_file` 分段读取。

**后端标准报告**：后端在工具结果中以 MCP `resource_link` 返回报告文件。agent 下载到工作区 `analysis-reports/<project_id>/`，记入文件改动日志，再经 `present` 交付。只接受 PDF、DOCX、HTML，以及 CycloneDX / SPDX 的 JSON、XML；限制单文件大小；下载地址必须与内置服务同源。

**定制解读报告**：新增内置技能「代码分析报告」，规定报告结构，并要求所有数字与结论引用后端数据。agent 按用户要求用 `office_create` 生成定制 Word 报告，结尾列出数据来源与后端报告原件。

## 5. 安全

- 后端返回的工具描述、结果与报告内容一律视为不可信数据。
- 内置服务地址必须 HTTPS（开发构建另允许回环）；请求 `redirect: 'error'`。
- 报告只从内置服务同源地址下载，拒绝后端结果中指向其他主机的链接。
- 第一阶段后端不鉴权，服务地址应部署在受控网络或仅用于联调；正式对外发布前必须完成第二阶段。
- `analysis_upload_source` 是代码离开本机的唯一入口，审批写明内容与大小，打包排除凭据文件。

### 分析对象的信任边界

通用模式下，工作区是用户自己的代码，按现有规则可信；分析的目标往往是第三方代码，不可信。信任边界因此跟着分析对象走，不跟着会话走：同一个会话可以先做通用编程、再做分析，工作区的信任状态不变。

- **分析对象不是工作区**：源码包、文件夹与 GitHub 仓库是被检查的数据。agent 只对它打包上传，不加载其中的 `AGENTS.md`、Skills、扩展、钩子与 MCP 配置，不在其中执行命令，也不读取其内容进对话；分析结论只来自后端结果。
- **工作区外的分析对象**：桌面入口「添加源码包或文件夹」可以选择工作区外的路径。该路径登记为本会话的分析对象，登记写入会话日志，只有 `analysis_upload_source` 能使用它；文件工具与命令对它仍按工作区边界拒绝。
- **GitHub 仓库**：由后端拉取，本地不落代码，天然满足上面的边界。
- **工作区内的分析对象**：用户分析自己项目里的代码时，按工作区现有信任规则处理，不额外隔离。
- **推荐路径**：分析第三方代码时，以分析对象方式添加，不要把它作为工作区打开。直接打开时，钩子仍受现有工作区信任确认约束，其余配置的整体隔离不在本期范围。

## 6. 错误处理

| 情况              | 行为                                                 |
| ----------------- | ---------------------------------------------------- |
| 断网 / 后端不可用 | 返回「服务暂不可用」；工具不注销；异步任务保留可再查 |
| 同步调用超时      | 返回超时错误；异步任务不受影响                       |
| 参数校验失败      | 本地拒绝，指出出错字段                               |
| 后端返回非法结果  | 返回通用错误，原始内容只记日志                       |

## 7. 需与后端约定的接口

1. 上传接口：路径、multipart 字段名、大小上限声明方式、返回 `{ project_id }` 的格式、错误码。
2. GitHub 拉取工具：名称与参数（URL、ref）。
3. 异步任务：慢工具返回 `{ task_id, status }`；状态、结果、取消三个工具的名称、参数与状态取值。
4. 工具注解：只读工具标注 `readOnlyHint: true`。
5. 报告文件：以 `resource_link` 返回，下载地址与 MCP 端点同源。
6. 鉴权：第一阶段不需要；第二阶段的约定见第 9 节。

## 8. 测试

- 单元测试：清单解析与哈希校验、保留前缀冲突、权限分类、工具名映射与上限、schema 校验、作业状态流转、请求构造函数是唯一出口、GitHub URL 校验、目录打包排除凭据、工作区外分析对象只对 `analysis_upload_source` 可用且文件工具与命令仍拒绝、添加分析对象不加载其中的配置。
- 集成测试：本地假 MCP 服务加 HTTP 上传接口，覆盖上传 → 同步分析 → 异步分析 → 取消 → Host 重启后找回 → 下载报告。
- 桌面 smoke：新增的 Electron smoke 测试必须登记到 `package.json` 的 `smoke:desktop`。

## 9. 第二阶段：登录与鉴权（预留）

第一阶段跑通后再设计与实现，这里只记录已讨论的方向：

- 在第 1 节的请求构造函数中接入令牌来源接口 `getAccessToken(options?: { refresh?: boolean }): Promise<string | undefined>`，放入 `Authorization: Bearer`；返回 `undefined` 表示未登录。
- 收到 401 时以 `{ refresh: true }` 再取一次并重试一次，仍失败返回「请先登录」；未登录时工具保持注册，调用返回同样的提示。
- 工具在 Host 进程执行，登录状态在桌面主进程：Host 经 `packages/carrier` 命令词表新增的一条受校验请求向桌面取令牌，令牌只在内存中传递，不写入环境变量、磁盘、日志、会话事件或工具结果。CLI 单独运行时没有登录状态。
- 后端约定：接受 `Authorization: Bearer <用户令牌>`，未授权返回 401；报告下载接受同一令牌。
