**Corrections:**

- Severity medium → low. The finding already concedes there is no shipped caller, and that is decisive: the desktop carrier vocabulary (`contract.ts:501-503`), the client (`session-controller.ts:813`) and the SDK never send `workspace.apply`, so today this is dead protocol surface. The only reachable trigger is a hand-written protocol client, which on the same connection can call `permission.update` (`handlers/system.ts:114-122`), `sandbox.set host` (`:72-112`), `run.start`, and answer its own `approval.respond` — i.e. finding 1's trust problem, not a distinct capability.
- The stated mechanism is slightly off. `approve: async () => true` is not the bypass: because `apply` never reads `input.context`, that callback is dead code that would never be invoked even if it were a real approver. The defect is the _absence of the pipeline_ on this path, not the callback's return value; the finding's own evidence (apply never reads `context`) actually supersedes its framing.
- "under a read-only file sandbox" overstates what existed to be bypassed: the file policy is a tool/process-level constraint (`registry.ts:608`, `handlers/system.ts:97`, `packages/tools/execution-environment.ts`), and no other mutating RPC method consults it either — `changes.undo` (`handlers/sessions.ts:77-88`) is the same shape. This is a surface-wide property, not something specific to `workspace.apply`.
- "The tool path is gated only because the tool declares `permission: 'write'`" understates the tool path: `registry.ts:608` also refuses write tools outright under a read-only policy.
- What survives intact is the documentation defect: `handlers/workspaces.ts:19-21`, `:80` and `packages/workspaces/results.ts:75-78` assert an approval that this code path cannot perform, and `handlers/workspaces.ts:111-116` proves it with `as never`. That is a genuine, verifiable invariant break for any embedding client, and the recommended fix (delete the false claim or route the RPC path through a real approver / a read-only refusal) is still the right one.

**Reasoning:** Every cited line contains what the finding says, and the code genuinely writes up to 64 paths / 8 MB into the parent execution root with no approval and no execution-policy check, contradicting two explicit in-code claims. But the consequence is not real for the shipped product: no shipped client can issue the method, the one path that can (a raw protocol client) already holds strictly greater power on that same connection, and the "read-only sandbox" that the finding presents as bypassed is not a property of any RPC write path. A false documented invariant plus an unguarded write path for embedders is a real but low-impact defect, so I confirm it at low rather than medium.
