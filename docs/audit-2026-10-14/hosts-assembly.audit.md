## CAPABILITIES

- `apps/agent-host/main.ts:24-87` is pure assembly in a fixed order: `resolveLaunch` → `openHostServices` → `createHostState` → `HostCarrier` → background wake → `createVerifier` → `TaskScheduler` → scheduler notifier → `createDispatcher` → `createRequestHandler` → `serveHost`. The three mutually referential slots (`carrier`, `scheduler`, `dispatch`) are written into pre-declared fields (`state.ts:172` returns `undefined as unknown as Slot`), and all of them are filled before `carrier.attach()` can run (`lifecycle.ts:87`).
- The dispatch table is a `Map` built from ten handler modules holding 57 method keys in total (counted from `apps/agent-host/handlers/*.ts`: background 6, compaction 1, files 3, history 4, interaction 2, runs 5, sessions 13, system 5, tasks 12, workspaces 6). `Map` is used deliberately so a wire method named `constructor`/`toString` answers `Unknown method` instead of something inherited (`dispatch.ts:31-57`).
- One request frame must be a JSON object with a nonempty string `id`, `params` must be an object (or absent), and a request id already being served is refused as `Duplicate pending request ID`; the id is released only when the request finishes (`dispatch.ts:88-110`). Every failure becomes the same `{id, error}` frame with code `HOST_REQUEST_FAILED` unless a `HostProtocolError` names one; the id slot holds `null` when the request had no usable id (`dispatch.ts:100-107`).
- Input size is checked as `Buffer.byteLength(line) > MAX_INPUT_BYTES` where `MAX_INPUT_BYTES = 16 * 1024 * 1024` (`dispatch.ts:84`, `packages/protocol/images.ts:7`). The check runs inside `handle()`, i.e. after readline has already assembled the whole line.
- The carrier is stdin/stdout by default; with `--listen [host:]port` it binds a TCP listener, accepts exactly one connection, and answers the next one with a single `{id:null,error:{message:'Agent Host already has a connected client…'}}` frame followed by `end()` (`carrier.ts:57-65`, `102-146`). `parseListen` defaults the host to `127.0.0.1` when the `host:` part is absent but accepts any `[^:]*` string, including `0.0.0.0` (`apps/shared/args.ts:148-154`). The bound port is printed on stdout because port 0 is allowed (`carrier.ts:139-143`).
- Frames on the wire are exactly `JSON.stringify(data) + '\n'`; a frame with no connected carrier is dropped and reported on stderr as `[host] dropped a message: no carrier is connected` unless the Host is closing (`carrier.ts:68-76`). Nothing on the carrier path awaits `write()`'s return value or a `drain` event (`carrier.ts:61`, `91`, `122`).
- Shutdown is one ordered, idempotent function: `closing = true` → stop observing background → `scheduler.stop()` → abort every active run → abort the manual compaction → settle pending approvals/questions → start resident disposal → close the carrier; then in `serveHost`'s `finally`: await every in-flight `handle()` promise, remove the signal listeners, run `sessionEnd` for each announced session plus the `session-close` invariant, then close terminals → background commands → store → hooks (`lifecycle.ts:20-38`, `102-135`). Failures are collected and rethrown as an `AggregateError` (`lifecycle.ts:137-139`).
- Sessions are checked for ownership by comparing the session's realpath-resolved workspace with the Host's single workspace; both "no such session" and "another workspace" produce the same refusal (`params.ts:34-44`). Every handler that resolves a session by id calls `ownedSession` before reading anything (46 call sites across `apps/agent-host/handlers/*.ts`); the two methods with an optional `sessionId` (`background.list`, `background.clear`) call it only when the field is a nonempty string (`handlers/background.ts:23`, `83`).
- Exclusivity is process-wide: a run reserves `ctx.active` before its first `await` (`run-start.ts:97-103`), and `run.start`, `plan.*`, `task.*`, `changes.undo`, `session.rename/delete`, `workspace.*` and `context.compact` all refuse with `Host is busy; wait…` while `ctx.active.size` or `ctx.restoring` is set (`run-start.ts:52`, `sessions.ts:61/69/80/103/110`, `tasks.ts:75/86/112/166/222`, `workspaces.ts:85/149/170/188`, `compaction.ts:27`).
- `TaskScheduler` (`scheduler.ts:65-309`) re-arms one `unref`'ed timer aimed at the earliest `nextRunAt`, with a 1000 ms floor and a 30000 ms ceiling/fallback (`scheduler.ts:50-51`, `100-122`); every due obligation is admitted through the compare-and-set `claimTaskSchedule`, which refuses a task whose `next_run_at` changed or whose rule revision differs and writes a `task.admitted` receipt (`session-tasks.ts:588-661`). Missed occurrences collapse to one run (`dueTasks(..., {catchUp})`), a `skip` misfire policy is applied only when the obligation is more than 60000 ms late (`scheduler.ts:223-232`), and event cascades are capped at `MAX_EVENT_DEPTH = 3` with a per-cascade task chain (`scheduler.ts:41`, `199-222`). Due work the Host cannot start is written as one delivery per session with reason `busy` or `closed` (`scheduler.ts:167-194`).
- A run that nobody asked for fails closed on approvals: an unattended task defers the approval (`DeferredApprovalError`) and a background wake denies it, while an ordinary run publishes `approval.required` and waits at most 120000 ms before resolving `false` with source `unavailable` (`approvals.ts:130-142`). Verification commands run outside a run use `createVerifier`, which honors the live permission policy and `--allow-write`/`--allow-command` and otherwise denies (`approvals.ts:53-74`). Questions use `YUANTU_QUESTION_TIMEOUT_MS` (default 120000 ms, `packages/protocol/settings.ts:165`) and settle as `unavailable` for scheduled/woken runs without sending anything (`approvals.ts:189-221`).
- Background wakes are coalesced per microtask and only run when a carrier is connected and `runtime.ready` has been received; one session is woken at a time and the wake re-checks `active`/`restoring`/`manualCompaction` (`background-wake.ts:62-116`). The sandbox and permission policy in force at admission are captured onto the session's background row (`background-wake.ts:37-61`), and the wake runs under that captured authority with its own wall clock (`run-start.ts:104-112`).
- `openHostServices` converges everything a dead Host left behind before serving: `reconcileInterruptedRuns`, `recoverInterruptedTasks`, `reconcileChildRuns`, `recoverInterruptedStreams`, `resumableTasks`, then `WorkspaceManager.reconcile` and `WorkspaceResultsService.reconcile` (`services.ts:46-72`).
- Agent assembly is per run, not per Host: `createAgent` builds a provider, a workspace manager, a tool registry and a capacity resolver on every `run.start` (`run-start.ts:224`, `apps/shared/runtime.ts:238-388`); the resolver calls `discoverAutomaticCapacities` when the configured route has no declared/known capacity (`runtime.ts:161-178`). Sub-agent children get their own registry rooted at their own execution directory (`runtime.ts:349-350`). Goal continuations are limited to `GOAL_CONTINUATIONS_PER_REQUEST` rounds and only for plain runs — not planning runs, task runs or approved-plan runs (`run-start.ts:313-323`).
- History is paged by count and by serialized size: at most 100 messages or 15000000 bytes per page, and when a single message is larger the display view receives it as 1000000-UTF-16-unit chunks; without `view:'display'` an oversized message is refused outright (`history.ts:97-126`). `session.audit` pages at most 500 (default 200) and `session.events` at most 500 (default 500) (`history.ts:143-152`, `167-181`). `session.get` with no `offset` is a separate, unpaged branch (`history.ts:22-36`).
- `files.list` sorts before capping at `FILE_TREE_ENTRY_LIMIT = 1000` and skips anything the `Workspace` resolver refuses (links, hidden/credential names, escapes), so the tree can only show paths `read_file` would also open (`files.ts:31-71`, `packages/protocol/rpc.ts:88`); `files.read` returns at most `FILE_PREVIEW_BYTES = 128 * 1024` of text, classifies by bytes (image signature, NUL byte) rather than by name, and returns base64 only for images up to `MAX_IMAGE_BYTES = 5 * 1024 * 1024` (`files.ts:80-126`, `packages/protocol/rpc.ts:89`, `packages/protocol/images.ts:6`).
- `background.poll` validates `cursor >= 0` and `0 <= waitMs <= 5000`, and falls back to the durable log for a job this process never owned (`background.ts:34-49`, `params.ts:53-85`).
- The paused entry points are refused before doing any work: `requireProductEntry('cli'|'web'|'acp')` is called at module top level (`apps/cli/main.ts:83`, `apps/agent-acp/main.ts:11`) and again at the start of `startBridge` plus the CLI-invocation guard (`apps/web/main.ts:203`, `424-426`), against `PRODUCT_SCOPE = {mcpManagement:false, cli:false, web:false, acp:false}` (`packages/protocol/product-scope.ts:2-12`). The CLI additionally refuses `--listen` with a message that names Agent Host's `--listen` as the way to serve externally (`apps/cli/main.ts:193-196`).
- The retained web bridge is loopback-only and token-checked (403 for a non-loopback remote, 401 for a missing/incorrect `?token=`), and refuses a second page by repeating the Host's own refusal sentence (`apps/web/main.ts:289-318`). Its retained WebSocket decoder implements exactly one text message per link: masked client frames required, minimum-length encoding required, 64-bit lengths refused above `MAX_WEBSOCKET_MESSAGE_BYTES = 64000000`, control frames ≤ 125 bytes, and a 64000000-byte cap on an assembled message (`apps/web/websocket.ts:40`, `111-156`, `180-243`).

## FINDINGS

### hosts-assembly-1 | high | security

**Title:** The TCP carrier has no authentication, and one connection is enough to grant OS-unsandboxed command execution
**Evidence:** `carrier.ts:102-146` accepts the first socket that connects and never inspects anything about it — no token, no `remoteAddress` test; the remote address is only logged (`carrier.ts:129-131`). `parseListen` defaults to `127.0.0.1` but accepts any host string (`apps/shared/args.ts:148-154`), so `--listen 0.0.0.0:8080` binds every interface. The connected peer can then (a) switch the process default sandbox to `host` via `sandbox.set` — `parseSandboxMode` accepts `'host'` (`packages/tools/sandbox-mode.ts:3-13`) and the handler only requires `ctx.active.size === 0` (`handlers/system.ts:72-111`); (b) install an allow-all permission policy via `permission.update`, which replaces `ctx.permissionPolicy` wholesale (`handlers/system.ts:114-119`); and (c) answer its own `approval.required`/`question.required` frames, since `approval.respond` settles whatever id it is given (`handlers/interaction.ts:15-23`). The retained web bridge does the opposite — loopback check plus a random `?token=` (`apps/web/main.ts:289-300`, token generated at `main.ts:80`) — and `README.md:545` documents only the one-connection limit, never authentication. The product actively points users here for network service: `README.md:523` and `apps/cli/main.ts:193-196` tell the user to "start the Agent Host with `--listen [host:]port`", and `carrier.ts:20-24` describes the socket as the supported carrier for any non-spawning client.
**Impact:** With the listener reachable (any local process on the default loopback bind, or anyone on the network after a routable bind that the docs recommend for "serving externally"), one connection owns the Host: workspace file writes, arbitrary command execution with the sandbox switched off and every approval self-answered. The documented "full permission needs one explicit confirmation" (`README.md:563`) is a desktop-UI property that the Host itself does not enforce.
**Recommendation:** Give `HostCarrier` the same trust gate the web bridge has — require a token (`--listen-token`/env, compared with a timing-safe compare) or refuse to bind any address other than `127.0.0.1`/`::1`, and reject `sandbox.set` to `host` over a socket carrier unless the process was launched with an explicit flag. Whatever is chosen, state the trust model where `README.md:545` documents the one-connection limit.
**Confidence:** high

### hosts-assembly-2 | high | reliability

**Title:** A second TCP connection that closes without reading the refusal crashes the Host with an uncaught `ECONNRESET`
**Evidence:** The served connection path attaches a readline interface, which installs an `error` listener on the socket (`carrier.ts:121-133`, verified: `listenerCount('error') === 1`). The refusal path does not: it writes the error frame and calls `end()` on a socket with no listener at all (`carrier.ts:107-120`). Reproduced with Node 24 in `.scratch/audit/exp-refusal2.mjs`, which runs exactly those three calls on a second connection: `UNCAUGHT=ECONNRESET`, exit 7 — for both an abortive reset (`socket.resetAndDestroy()`) and a plain `socket.destroy()` before the refusal payload is read. Nothing in the repository installs a process-level `uncaughtException` handler (grep over all `*.ts` finds only test-local `unhandledRejection` listeners), and `serveHost`'s `try/catch` cannot see it because the throw does not happen inside the `for await` read loop (`lifecycle.ts:84-101`).
**Impact:** The process dies abruptly, bypassing the entire teardown sequence in `lifecycle.ts:102-135`: the store is not closed, no `sessionEnd` hook or `session-close` invariant runs, and the pty terminals and background commands are never stopped — `lifecycle.ts:56-70` states these are the resources "with a process behind it", so their child processes are orphaned. Any in-flight run is left `in_progress` and only converged on the next start (`services.ts:47-55`). The trigger needs no malice — a port probe that connects and closes, or a client that quits before reading, is enough; the desktop's supervised carrier would then spend its three restart attempts.
**Recommendation:** Attach an error handler before writing on the refusal path — e.g. `candidate.on('error', () => {})` (or `candidate.destroy()` after `end()`), the same protection readline provides for the served socket — and add an `uncaughtException`/`unhandledRejection` guard in `apps/agent-host/main.ts` that logs through `safeError` and runs `shutdown` rather than dying silently.
**Confidence:** high

### hosts-assembly-3 | medium | security

**Title:** `workspace.apply` writes and deletes files with no approval and no execution-policy check, contradicting its own documented rule
**Evidence:** The module states the rule explicitly: "Writing through RPC needs the same approval as writing through a tool. `workspace.apply` … asks the run's approver — the one a person answers — rather than deciding for itself that a client is trusted" (`handlers/workspaces.ts:19-21`). The handler instead passes `approve: async () => true` and hides the shape mismatch behind `as never` (`handlers/workspaces.ts:111-116`); `WorkspaceResultsService.apply` never reads `input.context` at all (`packages/workspaces/results.ts:494-517`), and the write itself is raw `fs` work — `unlink`, `mkdir`, `atomicWriteFile` — with no `executionPolicy`/`requireExecutionCapabilities` call (`packages/workspaces/results.ts:1037-1064`). Up to `RESULT_LIMITS = {fileBytes: 1_048_576, files: 64, totalBytes: 8 * 1024 * 1024}` move per call (`packages/workspaces/results.ts:132-139`). The tool path is gated only because the _tool_ declares `permission: 'write'` and goes through the pipeline (`packages/tools/workspaces.ts:100-124`).
**Impact:** A client can import a sub-agent result — creating, overwriting and deleting up to 64 paths (8 MB) in the session's execution root — under a read-only file sandbox (`sandbox.set files:'read-only'`, `handlers/system.ts:97`) or a policy whose matching rule is `ask`, without any approval frame being sent. The Host's read-only enforcement is therefore not a property of the RPC surface. Reachability is limited: no shipped caller issues `workspace.apply` (grep finds only the handler, `packages/protocol/rpc.ts:175` and tests), so today the cost is a broken invariant plus an unguarded write path available to any embedding client.
**Recommendation:** Make the RPC path pass a real approver — the same construction `createVerifier` uses (`approvals.ts:53-74`) — and have `apply` call `context.approve` before `beginWorkspaceApply`, or refuse the method outright when `executionPolicy(...).files === 'read-only'`. If approval genuinely belongs to the tool pipeline only, delete the false claim at `handlers/workspaces.ts:19-21` and say in `packages/protocol/rpc.ts:175` that this method writes without an approval.
**Confidence:** high

### hosts-assembly-4 | medium | reliability

**Title:** JSONL framing has no bound in either direction while bytes are buffered
**Evidence:** Readline is constructed for the accepted transport (`carrier.ts:60`, `123`) with no maximum line length, so the `MAX_INPUT_BYTES` (16 MB, `packages/protocol/images.ts:7`) guard cannot run until a `'\n'` has arrived: the check is `Buffer.byteLength(line) > MAX_INPUT_BYTES` inside `handle()` (`dispatch.ts:84`), i.e. on a fully assembled string. The client-side framer has the missing half of this protection and the Host does not: `packages/client/host-transport.ts:82-85` fails the transport as soon as the _incomplete_ buffer exceeds `maxFrameBytes`. In the other direction, `process.stdout.write(line)` and `socket.write(line)` results are discarded (`carrier.ts:61`, `91`, `122`) and no `drain` is awaited, so a peer that stops reading does not slow the run down.
**Impact:** A peer that streams data with no newline makes the Host allocate memory proportional to the stream — the 16 MB refusal never fires — and on the socket carrier that peer needs no authentication (finding 1). Symmetrically, a client that stops reading (paused UI, a stuck/stalled consumer) lets stdout/socket buffering grow while the run keeps producing tool output and streaming deltas, with no cap and no backpressure signal.
**Recommendation:** Bound the reader rather than the parsed line: read the transport through `packages/client/host-transport.ts`'s `lineFramer` (or an equivalent byte-counting scan) with a 16 MB `maxFrameBytes`, and refuse/close the carrier on overflow. For output, treat a `write()` returning `false` as a reason to pause emitting (await `drain`) or to close a carrier that has been unwritable beyond a byte budget.
**Confidence:** high

### hosts-assembly-5 | medium | reliability

**Title:** `session.get` without `offset` returns the whole transcript in one frame and can exceed the client's frame limit, killing the link
**Evidence:** The unpaged branch returns `messages: history` — the entire stored transcript, including assistant `providerState`, since the `displayMessage` stripper is applied only in the paged branch (`handlers/history.ts:22-36` vs. `72-76`, `97-130`). The paged branch bounds a reply at 100 messages or 15000000 bytes and chunks an oversized single message; the unpaged branch has no equivalent bound. The client's `lineFramer` gives up permanently when one line or an incomplete buffer exceeds `maxFrameBytes` — default `64_000_000` — reporting `Agent Host response exceeds frame limit` (`packages/client/host-client.ts:136`, `packages/client/host-transport.ts:74-85`), which becomes `fail(error)` and a terminal `failed` status (`host-client.ts:312-313`). Sizes that make >64 MB reachable are the ones the suite already exercises: one Responses turn whose continuation state is 9 MB is reloaded through exactly this unpaged call (`tests/large-response.test.ts:180-230`), and images are stored base64 at up to `MAX_IMAGE_BYTES = 5 * 1024 * 1024` each with 10 MB permitted per request (`packages/protocol/images.ts:6`, `69`).
**Impact:** A long session (roughly eight large `providerState` turns, or a few image-bearing ones) makes the documented load-a-session call produce a frame the transport refuses; the Host builds that multi-megabyte string in memory first, and the client side marks the link failed — for a connected (socket) carrier there is no reconnect, so every later request on that client fails. A client that calls this method directly rather than the paged `readDisplayHistory` helper is the affected shape.
**Recommendation:** Apply the same page bound to the unpaged branch — return the paged shape by default (an implicit `offset: 0` + `view: 'display'`), or refuse with an explicit "use offset" error when the serialized transcript would exceed the 15 MB page budget — so that "load the session" can never emit a frame near the transport's 64 MB ceiling.
**Confidence:** medium

### hosts-assembly-6 | low | correctness

**Title:** A manual compaction cannot be cancelled: `run.cancel` reports `cancelled:false` while it keeps spending
**Evidence:** `run.cancel` is the Host's only cancellation method (`dispatch.ts:38-49`, handler list in `README.md:535`) and it aborts exactly `ctx.active.get(sessionId)?.controller`, then closes the session's background commands and returns `cancelled: !!run` (`handlers/runs.ts:57-72`). `context.compact` does not appear in `ctx.active`: it sets `ctx.manualCompaction = controller` and `ctx.restoring = true`, and only the shutdown path ever aborts that controller (`handlers/compaction.ts:60-62`, `lifecycle.ts:27`). The compaction request itself is bounded by `summaryTimeoutMs`, default 120000 ms (`packages/protocol/settings.ts:157`), and the handler never calls `ctx.carrier.send` — `onCompaction: () => {}` discards the only progress callback it is given (`handlers/compaction.ts:126`), so nothing tells the client it is still running.
**Impact:** A user who starts `/compact` and then cancels gets `{cancelled:false}` — and, while `ctx.restoring` stays true, every other mutating method refuses with `Host is busy; wait…` (`compaction.ts:27`, `tasks.ts:75`, `sessions.ts:61`, `workspaces.ts:85`) for up to the 120 s summary timeout. The summarization request keeps running and keeps billing after the stop request, with no event telling the client it is still in flight.
**Recommendation:** Give the compaction a cancellation handle the client can reach: have `run.cancel` abort `ctx.manualCompaction` too (returning `cancelled:true` when it did), or add an explicit `context.compact.cancel` method; and emit a start/finish event for manual compaction so the client can distinguish "nothing to cancel" from "still running".
**Confidence:** high
