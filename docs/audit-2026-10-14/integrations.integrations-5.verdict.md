**Corrections:**

- Line citation for the Responses mapping is imprecise: `responses.ts:224-231` only detects the `incomplete` event; the `finishReason: 'length'` assignment is at `responses.ts:263`. Same code path, so this does not change the verdict.
- "the adapters already have a `truncation`/diagnostic channel" is overstated: `ModelResponse.truncation` is a single-valued `'context-window'` field (`packages/protocol/index.ts:166-173`) and `OutputDiagnostics` (`:155-160`) has no filter field, so carrying the filter outcome is a protocol change, not a reuse of an existing slot. The recommendation is still the right shape, just not free.
- The tests bake the Responses behaviour in (`tests/providers.test.ts:872-875` asserts `finishReason === 'length'` for an incomplete terminal), so this is an intentional simplification rather than an oversight — which is an argument for keeping the severity at low, not for calling the finding wrong.
- Severity stays `low`: I could not reach a case where the user is told the run succeeded. The chat path does not silently accept a filtered turn (it fails with `empty-response`), and the Responses path fails the run with a wrong-cause `limited` error. The measurable cost is bounded re-sends (≤5) plus a misleading reason string and, in the summary path, ≤`retriesLeft` wasted attempts.

**Reasoning:**
Every code fact in the finding holds up under reading: `content_filter` is folded into `'stop'` (`openai.ts:308-309`), `response.incomplete` is unconditionally labelled `'length'` (`responses.ts:260-264`) with `incomplete_details.reason` read nowhere in source, and the core does branch on both labels exactly as claimed (`agent.ts:2766-2780`, `2831-2881`, `context.ts:948-972`). The protocol-level existence of `content_filter` as an incomplete reason is confirmed externally, and nothing in the repo's documentation declares this mapping deliberate or harmless. The consequences are genuine but strictly bounded (retry budget 5, `output-limit` is non-retryable, the summary retry is capped), so this is a real low-severity correctness/diagnostics defect rather than a high-impact one.
