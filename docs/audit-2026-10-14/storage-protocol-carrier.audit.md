## CAPABILITIES

1. One SQLite file per workspace holds sessions, the event log, tasks, workspaces and attachment blobs; the newest shape is defined exactly once (`packages/storage/session-current-schema.ts:33`) and `SCHEMA_VERSION = 30` (`packages/storage/session-schema.ts:391`) is the value stamped into `PRAGMA user_version`.
2. An empty file is created in a single transaction that also writes the `application_marker` row and `user_version` (`packages/storage/session-migrations.ts:100-115`); an existing file is first given a `CREATE TABLE IF NOT EXISTS` parity block outside that transaction (`session-migrations.ts:126-345`) and then the ordered `migrations()` steps, each carrying its own `fromVersion` guard, inside one transaction that claims the marker and stamps the version last (`session-migrations.ts:346`, `450-453`, `538`).
3. Version gating is explicit in both directions: `user_version > 30` is refused with `Unsupported session database version: N` after the connection is closed (`session-migrations.ts:66-70`); a foreign `PRAGMA application_id` (`APPLICATION_ID` is derived from `sha256('yuantu-agent')`, `session-schema.ts:338-343`) or a marker whose `application` differs or whose `format` exceeds `APPLICATION_FORMAT = 1` is refused as another application's file (`session-migrations.ts:42-65`, `session-schema.ts:350`).
4. Upgrades are backup-first: when `version < 30` and the file already has a `sessions` table, a snapshot is taken with `VACUUM main INTO ?` before any DDL, and a snapshot failure aborts the migration rather than proceeding without one (`session-migrations.ts:71-86`, `packages/storage/database-maintenance.ts:341`).
5. Every connection sets `busy_timeout = 5000`, `journal_mode = WAL` and `foreign_keys = ON` (`session-migrations.ts:87`); within a workspace, cross-process exclusion is a directory lock (`<db>.maintenance-lock`) plus a `.users/` registry of per-process token files whose owner is judged dead with `process.kill(pid, 0)` (`database-maintenance.ts:100-165`, `191-202`, `session-schema.ts:315`).
6. `session_events` is `(seq INTEGER PRIMARY KEY AUTOINCREMENT, session_id, type, data, at)` with an index on `(session_id, seq)` (`session-current-schema.ts:62-69`); `seq` is global rather than per session, which is what lets one integer serve as a client cursor.
7. The durable event vocabulary is the closed set `SESSION_EVENT_TYPES`, and `assertKnownEvents` refuses a log containing a type that is neither known nor listed in `IGNORABLE_SESSION_EVENTS` (`packages/storage/events.ts:28`, `309`, `369-374`, `406`), so a truncated or unknown log is reported instead of half-applied.
8. Ten built-in projections are registered in one place (`packages/storage/projections.ts:672-683`); all but `messages` persist checkpoints, and a checkpoint is used only when its fold identity matches, its `seq` exists in the log, its state is shaped like that projection's own, and replaying the event it claims to include still returns a state of that shape (`packages/storage/session-checkpoints.ts:92-93`, `215-239`, `packages/storage/session-schema.ts:441-473`); otherwise the log is re-folded from the start (`session-checkpoints.ts:112-130`).
9. Checkpoint writes cannot fail a run: they are wrapped and their errors are swallowed, and a checkpoint naming a `seq` the log no longer holds is refused rather than used (`packages/storage/session-checkpoints.ts:156`, `227`, `packages/storage/sqlite.ts:2383-2385`).
10. Transcript folds are cached for the 8 most recently used sessions (`LOG_CACHE_ENTRIES = 8`, `session-schema.ts:490`) and invalidated by `PRAGMA data_version` changing (`sqlite.ts:1383-1411`); message appends are buffered up to `APPEND_BATCH_LIMIT = 64` per session (`session-schema.ts:478`, `sqlite.ts:1676-1679`) and are written by a read of that session, by any event recorded for it, by the tool barrier, and by close (`sqlite.ts:1027`, `1691-1713`).
11. Leases are presence, not expiry: `beginRun` writes the run row and the `session_leases` row in one transaction, `finishRun` deletes the lease, and nothing ages a lease out — a holder in another process is found with `process.kill(pid, 0)` and a `deadOwner` pid is what makes a lease stale (`sqlite.ts:2209-2228`, `2399-2401`; `session-schema.ts:315`; `packages/storage/session-workspaces.ts:96-101`). The protocol asks for renewal every 10 s (`packages/protocol/session-lease.ts:37`), and compaction is serialised by `session_leases.compacting_run_id`, re-checked inside the writing transaction (`sqlite.ts:1889-1955`, `2285-2300`).
12. File-change snapshots are bounded at 100 paths per group, 20 000 000 bytes per before/after image and 40 000 000 bytes per group, and a group is written in one transaction (`packages/storage/session-file-changes.ts:37-47`, `48-68`).
13. Search is SQLite FTS5 (`unicode61`) over `messages.search_text`, maintained by insert/delete/update triggers (`session-current-schema.ts:282-291`); user text never reaches `MATCH` verbatim because `ftsQuery` is its only producer (`packages/storage/session-search.ts:104-106`); query length (200), sessions (`MAX_SEARCH_SESSIONS = 10`) and matches (`MAX_SEARCH_MATCHES = 5`) are clamped inside the store rather than trusted from the caller (`session-search.ts:104-111`, `session-schema.ts:54-55`), and the page cursor is base64url `{v:1,offset}` with any other version refused (`session-schema.ts:90-111`).
14. Image bytes are content-addressed by sha256 in `attachment_blobs` and referenced from message bodies by hash; hydration restores the original key order and throws when a blob is missing (`sqlite.ts:1264-1279`), while pre-v21 databases whose messages still carry inline `data` keep reading (`packages/storage/session-blobs.ts:24-73`).
15. The carrier vocabulary is one closed union, `CarrierCommand`, parsed by `parseCarrierCommand` against a per-type key allow-list: unknown types and unknown keys are refused and every value is bounded (ids 128, paths 4096, titles 200, prompt 100 000, answers ≤ 4 with ≤ 6 selected and 4000-char free text, `subagent.transcript` ≤ 200 messages) (`packages/carrier/contract.ts:182-506`). The package imports only `client`, `protocol`, `core` and `tools` — no Electron, no DOM, no app module.
16. The Host wire is JSON-lines with `HOST_PROTOCOL_VERSION = 1` and a version offer of at most 16 entries (`packages/protocol/host-wire.ts:27-49`); the client frames incrementally, caps a frame at 64 000 000 bytes, a request at 16 MB, a request's wait at 10 s and shutdown at 10 s (`packages/client/host-client.ts:133-139`, `packages/protocol/images.ts:7`); a transport failure rejects every pending request with `HostDisconnectedError`, and the carrier restarts the Host at most 3 times with a 250 ms pause (`packages/carrier/service.ts:28-29`).
17. Live delivery is an allow-list: only types in `AGENT_EVENT_TYPES` are forwarded (`host-client.ts:73`), and the consumer applies a frame only when it belongs to the session being shown and to the run being watched, with a single `run.finished` exception so a Host that never named its run cannot leave the window stuck on "running" (`packages/client/session-controller.ts:1138`, `1163`).
18. Divergence between the log and the tables is checked by name: `storage.log-tables-agree` re-reads the fold, the transcript and the rows at the end of a run and compares them as JSON strings (`packages/storage/invariants.ts:31-55`).
19. Session deletion removes delegated descendants, then rows in dependency order (`file_changes`, `messages`, `run_stream_checkpoints`, `runs`, `session_events`, `task_attempts`, `tasks`, then `sessions`), then each attachment blob that no surviving row still references (`packages/storage/session-lifecycle.ts:121-167`, `193-212`).

## FINDINGS

### storage-protocol-carrier-1 | high | reliability

**Title:** A session database larger than 512 MiB can never be upgraded: the mandatory pre-migration snapshot is capped by the backup retention budget, and exceeding it makes the newer build refuse to open the workspace.
**Evidence:** `database-maintenance.ts:38` fixes `DEFAULT_BACKUP_POLICY = { maxCount: 5, maxBytes: 512 * 1024 * 1024 }`, and `database-maintenance.ts:311` is the only default for the `retention` argument — no production caller overrides it (`SessionStore`'s constructor accepts `{ backupRetention }` at `sqlite.ts:277`, threaded through `session-migrations.ts:78`, but the only caller that ever sets it is `tests/database-maintenance.test.ts:177`). `createBackup` runs `VACUUM main INTO ?` into a staging file and then refuses the snapshot outright when it is bigger than the budget: `if (inspection.bytes > retention.maxBytes) throw new Error(\`Snapshot exceeds backup capacity (${retention.maxBytes} bytes): ${source}\`)` (`database-maintenance.ts:341-344`). `session-migrations.ts:71-86`takes exactly that snapshot before any migration step and converts its failure into`Migration stopped because its backup failed: …`, which propagates out of `new SessionStore(file)`, so the workspace never opens. The same cap applies to the manual paths: `SessionStore`-free `db-backup` (`apps/cli/main.ts:205`) and the desktop's `create` backup worker (`apps/desktop/database-backup-worker.ts:22`) both call `createDatabaseBackup`with the default.`packages/client/host-client.ts:108-127`classifies startup failures by regular expression and has a pattern for`Unsupported session database version`but none for this message, so the desktop shows the raw English text.
**Impact:** A workspace whose`sessions.sqlite`reaches 512 MiB of live data (after`VACUUM INTO`, so this is real content, not free pages) cannot be opened by any build that needs to migrate it: the Host exits during startup on every launch, the failure is not recognised by the client's diagnosis, and every in-app recovery tool hits the same ceiling — `db-backup`cannot produce a snapshot to restore from either. The only ways out are deleting data by hand or restoring an older, smaller backup and losing everything since. README:378 presents 512 MiB as the retention budget ("备份最多保留 5 份、合计 512 MiB") and README:735 documents that an upgrade snapshots first and stops if the snapshot fails, but neither states that 512 MiB is also a hard ceiling on the size of a database this product is willing to migrate.
**Recommendation:** Do not let a retention budget gate the migration safety net. Either raise/ignore`maxCount`/`maxBytes`for the migration snapshot specifically (retain it outside the rotation, e.g.`pre-migration-<version>-<timestamp>.sqlite`), or make the cap a percentage of free disk space rather than a constant, and add a `SESSION_MIGRATION_BACKUP_TOO_LARGE`-style diagnosis with a documented recovery path (e.g. `db-backup --no-retention-cap`) instead of a dead end.
**Confidence:** high for the code path (the throw, the wrapper and the missing override are all as cited); medium on how often a live database passes 512 MiB, which the audit did not measure.

### storage-protocol-carrier-2 | medium | reliability

**Title:** Deleting a session permanently orphans its sub-agent worktree: the binding's session reference is nulled by the foreign key and every workspace cleanup RPC is addressed by session id.
**Evidence:** A worktree binding is created `preparing` with a nullable session (`session-current-schema.ts:213-226`: `session_id TEXT REFERENCES sessions(id) ON DELETE SET NULL`) and `attach` then sets it to the _child_ session (`session-workspaces.ts:352-388`). `deleteSessionRows` removes the session and the tables listing file changes, messages, stream checkpoints, runs, events, attempts and tasks, but never touches `workspace_bindings` (`session-lifecycle.ts:146-167`), so the FK action nulls the reference and the row stays `ready` with its `execution_root`. The Host's `session.delete` handler closes background jobs and terminals, runs the `sessionEnd` hook, then `ctx.store.delete(id)` and deletes the sandbox bookkeeping — with no workspace step of any kind (`apps/agent-host/handlers/sessions.ts:107-139`). All three cleanup methods take a session id and resolve from it (`apps/agent-host/handlers/workspaces.ts:146-199`: `manager.resolve(sessionId)`), `resolve` reads the row by `session_id=?` and calls `port.sessionProject(sessionId)` first (`packages/workspaces/manager.ts:128-130`, `session-workspaces.ts:225-230`, `255-256`), and that call is `SessionStore.get`, which throws `Session not found` for a deleted id (`sqlite.ts:1024-1034`) — so after deletion no RPC can name the binding at all. `WorkspaceManager.reconcile` does not cover the case either: it resolves `archiving`/`removing`/`preparing` rows and re-validates `ready`/`blocked` rows (`packages/workspaces/manager.ts:488-554`), and its only removal path, `removeOwned`, is reachable only through `remove(bindingId)` ← `workspace.remove` ← a session id (`manager.ts:643-660`).
**Impact:** Every write-capable delegated sub-agent creates a git worktree, and deleting the conversation (or the child session, which a parent's deletion also removes) leaves the directory, its `.git/worktrees/<name>` registration and a `ready` binding row behind forever. Disk use grows with past delegations rather than with live work, the user's repository accumulates entries in `git worktree list` that the product can no longer clean up, and each orphan is re-validated with a `git` call on every Host startup (`manager.ts:531-554`). README:466-477 describes worktree isolation and its boundaries but never says what happens to the directory when the session owning it is deleted.
**Recommendation:** Tear the workspace down before `store.delete(id)` — archive then mark `removing` for each binding of the session and of its delegated descendants — or add a by-binding-id cleanup RPC (`workspace.remove {bindingId}`) plus a `reconcile` pass that removes/marks `ready`/`blocked` bindings whose `session_id` is NULL and whose state has no owner.
**Confidence:** high (the FK action, the missing cleanup call, the session-keyed resolution and the throwing lookup are all cited above).

### storage-protocol-carrier-3 | medium | performance

**Title:** The retry counter is queried without a session scope from its only production caller, so every retry decision scans the whole workspace event log.
**Evidence:** `sqlite.ts:1774-1783` builds `SELECT COUNT(*) FROM session_events WHERE [session_id=? AND] type='llm.retry' AND json_extract(data,'$.runId')=? AND json_extract(data,'$.round')=?` and its own comment says callers that know the session pass it. The single production call site does not: `packages/core/agent.ts:2534` is `store.retryCount(runId, round)`, while `input.sessionId` is in scope in that very closure (used at `agent.ts:2506`). Without the session clause there is nothing to seek on: the table's only index is `(session_id, seq)` (`session-current-schema.ts:69`), `type` is unindexed, and the log is never pruned, so the query degenerates to a full scan of every event in the workspace database with two `json_extract` evaluations per row.
**Impact:** The cost of deciding whether to retry is proportional to the size of the entire workspace's history rather than to the run, and it is paid on the path that is already failing (provider errors, timeouts, overload). With a 500 000-event log and a run that retries 40 times, that is ~20 million row visits of pure overhead executed on the Host's synchronous SQLite driver, i.e. event-loop stalls precisely when the session is already degraded; the cost also grows for every other session sharing the database, including ones untouched by the failing run.
**Recommendation:** Pass the session id at `packages/core/agent.ts:2534` (`store.retryCount(runId, round, input.sessionId)`), which the method already supports and which turns the query into an index seek; consider an index on `session_events(session_id, type)` if other `json_extract`-filtered lookups are added.
**Confidence:** high (query, index list and call site are cited; the missing argument is a one-token fix).

### storage-protocol-carrier-4 | low | performance

**Title:** Nothing in the product ever returns disk space to the filesystem, and no maintenance path runs a plain `VACUUM` or `auto_vacuum`.
**Evidence:** A repository-wide search for `VACUUM|auto_vacuum|incremental_vacuum` in TypeScript returns exactly two statements, both `VACUUM main INTO ?`, which writes a _copy_ for a backup or restore stage (`database-maintenance.ts:341`, `502`); plain `VACUUM`, `PRAGMA auto_vacuum` and `PRAGMA incremental_vacuum` appear nowhere, and no table is created with anything other than the default `auto_vacuum = 0`. Deleting a session frees rows but leaves the file at its high-water mark (`session-lifecycle.ts:146-167`), and the delivered maintenance surface is backup, verify, restore and recover with nothing that rewrites the live file in place (`database-maintenance.ts:258-303`, `458-562`; `apps/cli/main.ts:197-208`).
**Impact:** Deleting a conversation that held gigabytes of tool output, events and image blobs reclaims no file bytes — the pages are reused by later writes at best — so `sessions.sqlite` only ever grows within a workspace. That growth feeds finding 1 directly: the file can pass the 512 MiB migration-backup ceiling while the user's live data is well under it, at which point the workspace stops upgrading with no supported way to shrink it.
**Recommendation:** Add an offline compaction step to the existing `assertOffline`-guarded maintenance CLI (`database-maintenance.ts:191-202`), i.e. `PRAGMA incremental_vacuum` on databases created with `auto_vacuum = INCREMENTAL`, or a whole-file `VACUUM` (plus WAL checkpoint) behind an explicit `db-compact` command; set `auto_vacuum = INCREMENTAL` in `createCurrentSessionSchema` for new databases so the option exists later without a full rewrite.
**Confidence:** high that no reclamation path exists (verified by search); medium on the practical size of the effect, which depends on user deletion habits the audit did not measure.
