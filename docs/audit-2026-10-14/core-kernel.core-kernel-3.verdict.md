**Corrections:**

1. Impact is overstated in wording, not in kind. "The learned factor drifts on evidence nobody measured" is wrong: the numerator is a real provider-measured residual (`sample` at `calibration.ts:163`). What is wrong is only the denominator/step size — `current` is the correction a request _whose byte mix equals the weights_ would get, which the summary request's mix generally does not. Correct statement: the step applied to all three weights is mis-scaled by `(Σw²/Σw) / blendFactors(w, actual summary bytes)`.
2. "A request that was estimated exactly right still moves every weight" is not a consequence of `sample = 1` alone. `sample = actual/rawEstimate` is the ratio against the _uncorrected_ estimate (`forecast.ts:43-44`); it means "estimated exactly right" only if the request's true blend over its own bytes is ≈1, which the finding asserts ("the request's own correction is ≈1") without showing a byte mix. It is a legitimate hypothetical (a messages-dominated transcript gives blend ≈ messages weight = 1), but it should be labelled as the chosen mix, not as a fact about summary requests.
3. Direction inversion is possible but small, and should not be sold as the main cost. With weights `{0.5, 0.5, 3}` (current = 2.375) and a messages-dominated summary (true blend 2.75), a provider answer of `sample = 2.5` — a genuine 10% overestimate that calls for a decrease — moves all weights _up_ by ~2%. The larger magnitudes run the other way: weights `{3, 0.5, 0.5}`, messages-dominated summary, true blend 0.5, `sample = 0.5` → `move = 0.684`, i.e. the messages weight lands 32% below the endpoint's own measurement.
4. "Every compaction after the first" is the wrong trigger. The branch is gated on `samples !== 0` (`calibration.ts:164`), not on compactions: the _first_ compaction of a resumed run (or of any run that has had one answer round) already takes it, and only a compaction that is the run's very first observation takes the adopt-whole path.
5. `agent.ts:2250` / `context.ts:889-900` show the code comment's premise at `calibration.ts:153-155` ("the caller cannot name the parts, which is all the caller knows") is false at this call site: `summaryForecast.bytes` is in scope two lines above `:946`, and `forecast.ts:45-53` explicitly carries `bytes` on the forecast _because_ "an observation needs to say which part was misestimated". The recommendation is therefore a one-argument change with no new computation, which argues the omission is an oversight rather than a forced simplification — this part of the finding is stronger than written, and worth stating.
6. The impact sentence "the learned factor ... prices the retained tail, the shrink cut sizes and the 'does this fit' verdict" conflates two numbers: the tail/shrink use the messages weight (`context.ts:364`, `:713`), while the fit verdict uses the three-part blend inside `measureRequest` (`budget.ts:153`). Cosmetic, but a reader checking the claim would find `factorFor` has no call site outside `calibration.ts`. Mitigations the original omits: `WEIGHT = 0.4` and the 0.5–3 clamp (`calibration.ts:40-47`) bound the effect; the shape (ratios) is preserved because the move is a single multiplicative factor; and every subsequent answer round re-observes _with_ parts, pulling the weights back toward the endpoint's measurement. So the mis-scaling is transient and diluted — which is why low, not medium, is right.

**Reasoning:** Every cited mechanism checks out against the source: the summary observation passes no parts, `parts ?? this.weights` inside `if (!parts)` provably blends the weights with themselves, and `blendFactors` is a byte-share average, so `current = Σw²/Σw` — a number the summary request never earned. The consequence is real but bounded: the weights are nudged by a step that can be several times the measured residual (or, in strongly skewed mixes, the wrong sign at ~2%), affecting the compaction's own retained-tail and fit arithmetic at exactly the moment those weights are used, then diluted by later part-carrying observations and clamped to 0.5–3. I keep the severity at low: it is a mis-scaled correction, not a wrong measurement, in a subsystem README.md:418 already documents as an approximation, and it cannot corrupt state or spend tokens by itself. The finding survives with the framing corrections above; its strongest form is not the `sample = 1` hypothetical but the fact that `summaryForecast.bytes` was sitting unused two lines below the call.
