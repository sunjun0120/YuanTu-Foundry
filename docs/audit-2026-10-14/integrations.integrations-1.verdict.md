**Corrections:**

1. Wrong mechanism for the sandbox, right conclusion. The finding says hooks run "outside the tool-dispatch `AsyncLocalStorage` policy", so the mode resolves from `YUANTU_SANDBOX`, "i.e. the `native` backend". In the shipped host path that is not how it works: `apps/agent-host/state.ts:227` (SessionStart), `lifecycle.ts:115` and `handlers/sessions.ts:129` (SessionEnd) all wrap the hook call in `underSessionPolicy`, which builds an `ExecutionPolicy` and installs it with `withExecutionPolicy` (`packages/tools/execution-policy.ts:80-82`). `resolveSandboxConfig` (`packages/tools/sandbox-provider.ts:150-157`) then takes `fixed.mode`/`fixed.files`, exactly as `README.md:628` documents. The hook ends up on `native` because the desktop launches the host with `YUANTU_SANDBOX=native` (`sandbox-environment.ts:40-49`) and the presets use `native`, not because no policy is installed. The residual-confinement judgement survives; the stated reason does not.
2. The `SessionEnd` half of "two of the six events" is moot for the read-only gate: `SessionEnd` fires only on `session.delete` (`apps/agent-host/handlers/sessions.ts:130`) and host shutdown (`lifecycle.ts:116`) — never as part of a plan/read-only run, so there is no scenario in which the missing gate changes anything there. It is a type-level inconsistency, not an execution path.
3. The plan-mode framing is narrower than the title implies. `session.create` announces the session (`sessions.ts:91`) before any run exists, so a workspace's SessionStart command runs at session creation in _every_ mode; adding a `readOnly` field would not have prevented that. The gate would only bite in the resumed-session case where `run.start` performs the first announcement (`run-start.ts:115`). The observe-preset case is real but has nothing to do with the gate: `readOnly` is plan-derived (`packages/core/agent.ts:596`), so the preset never suppressed any of the four gated events either.
4. The "workspace-declared commands execute, enabled by default, opt-out via env" property is the bridge's documented deliberate design (`README.md:370,628,640`), not an undocumented defect, so that half is context rather than the finding. What is genuinely wrong is the bridge's own stated gate 3 (`hook-bridge.ts:28-29`) failing for the lifecycle events, and the unstated consequence that a mode whose promise is "nothing outside the process is affected" still spawns a workspace command with network and out-of-workspace read access on Windows.
5. Minor: `apps/desktop/permission-settings.ts` has no `observe` preset (the name lives in `apps/desktop/permission-presets.ts:27`, mapping `observe` → read-only). The cited lines are otherwise accurate.

**Reasoning:** The code facts are real and I reproduced each cited line: SessionStart/SessionEnd spawn workspace-declared commands with no readOnly guard, no approval, and no permission-policy consultation, and those contexts cannot even see `readOnly`, so the bridge's own four-gate comment is false as written for two of its six events. That is a genuine behavioural gap in a shipped path (`apps/shared/runtime.ts:291` → `createTools` with the default enabled bridge), and the plan-mode/resumed-session path shows a run that promises no outside effects still spawning a workspace command. It is not "high", however: the underlying property — a cloned workspace's own hook config running its commands, opt-out by environment only — is the documented, deliberate Claude-Code-compatibility design that the project ships on purpose, and the "even in a read-only run" impact is narrower than stated because the hook normally fires at session creation and because SessionEnd is never a run at all.
