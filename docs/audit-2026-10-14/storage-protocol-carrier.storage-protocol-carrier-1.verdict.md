### storage-protocol-carrier-1 | confirmed | medium

**Checks:**

- `packages/storage/database-maintenance.ts:38` — `DEFAULT_BACKUP_POLICY = { maxCount: 5, maxBytes: 512 * 1024 * 1024 }`, exactly as cited.
- `database-maintenance.ts:306-315` — `createDatabaseBackup(..., retention: BackupPolicy = DEFAULT_BACKUP_POLICY)`; `database-maintenance.ts:341-344` — after `VACUUM main INTO ?` into a staging file, `if (inspection.bytes > retention.maxBytes) throw new Error('Snapshot exceeds backup capacity (...)')`, i.e. the snapshot is refused _before_ `renameSync` publishes it, and the `catch` at 383-392 removes the staging file. The cited line numbers are exact.
- `packages/storage/session-migrations.ts:71-86` — the snapshot is taken only when `file !== ':memory:' && version < SCHEMA_VERSION && this.hasTable('sessions')`, and its failure is rethrown as `Migration stopped because its backup failed: ...`, which propagates out of the `SessionStore` constructor.
- `packages/storage/sqlite.ts:277` (option) and `390-391` (`initialize` forwards it) — the only way to change retention. A repo-wide grep for `backupRetention|createDatabaseBackup|DEFAULT_BACKUP_POLICY` finds exactly one override, `tests/database-maintenance.test.ts:177`; no production caller sets it. The only production `SessionStore` construction is `apps/shared/runtime.ts:236` (via `apps/agent-host/services.ts:46`), with no options.
- `tests/database-maintenance.test.ts:162-186` — the behaviour is deliberately pinned: `new SessionStore(file, { backupRetention: { maxCount: 2, maxBytes: 1 } })` must throw `/capacity/i` and must leave `user_version` at `SCHEMA_VERSION - 1`. So the fail-closed refusal is intended, not accidental.
- `apps/cli/main.ts:197-212` — `db-backup` calls `backupDatabase(options.db!, SESSION_DATABASE_POLICY)` with no retention argument; `apps/desktop/database-backup-worker.ts:22` does the same for `create`. Both inherit the 512 MiB cap.
- `apps/agent-host/services.ts:46` + `apps/agent-host/main.ts:88-91` — `openStore(options)` is unwrapped, so the throw reaches `main().catch`, writes to stderr and sets exit code 1: the Host dies before serving, on every launch.
- `packages/client/host-client.ts:108-127` has no pattern for this message; `258-264` appends only a matched diagnosis to the RPC error; `300-305` rejects pending requests with `Agent Host exited (code=1, ...)`; `315-317` keeps stderr only in a private 4096-char tail that the comment at `106` says is "never returned verbatim".
- `README.md:378` states the budget as retention ("备份最多保留 5 份、合计 512 MiB") plus "备份失败则拒绝迁移"; the `已知边界` section (`README.md:713-736`) never mentions a database-size ceiling. The audit's documentation claim is accurate.
- Extra evidence the audit missed, which broadens the impact: `packages/maintenance/desktop-upgrade.ts:205-209` runs `backupDatabase(db, policy)` with default retention on the _shipped in-app upgrade path_ (`apps/desktop/upgrade-worker.ts:44-51`, surfaced at `apps/desktop/main.ts:213-217`), contradicting its own comment at line 206 ("Upgrade recovery copies are not subject to routine migration backup retention"). So the cap blocks ordinary upgrades for a >512 MiB database today, with no pending migration required. And `packages/storage/session-file-changes.ts:43-47` stores before/after images as BLOBs in that same database (20 MB per file, 40 MB per group, up to 100 paths), so ~13 full-size groups reach the ceiling — the size is attainable, not theoretical.
- `database-maintenance.ts:261-303` (`inspectDatabase`, read-only) has no size check, so `db-verify`/inspection and restoring an _older, smaller_ backup still work; only creating a snapshot of the oversized file is refused.

**Corrections:**

1. Severity high → medium. The code path, the missing override and the dead end are all real, but the failure is gated on a >512 MiB live database _and_ (for the migration case) a file below `SCHEMA_VERSION` with an existing `sessions` table. The refuse-to-migrate-without-a-backup rule is deliberate and test-pinned (`tests/database-maintenance.test.ts:162-186`), and the auditor itself admits the size threshold was never measured. High impact if hit, low-to-moderate likelihood.
2. "the desktop shows the raw English text" is wrong as stated. The stderr tail is deliberately not returned to the user (`host-client.ts:106`), and no diagnosis pattern matches this message, so what surfaces is the generic `Agent Host exited (code=1, signal=null); requests were not replayed` — the actual cause is _invisible_, which is a different (and slightly worse) defect than "untranslated English".
3. The audit understates one part: it frames the ceiling as a migration-only problem and mentions `db-backup`, but the same default-retention call also gates the desktop's in-app upgrade (`desktop-upgrade.ts:205`), for any oversized database, with no schema bump needed. The claim that "every in-app recovery tool hits the same ceiling" is right in spirit; the reachability is higher than the finding's own framing.
4. "cannot be opened by any build that needs to migrate it" should be qualified: a current-version (`user_version = 30`) file of any size opens normally (no backup is taken), and read-only inspection/restore-from-older-backup remain available (`database-maintenance.ts:261-303`, `486-525`). The hard stop is specifically "an oversized file that must be migrated or upgraded".

**Reasoning:** Every cited line contains what the finding claims, the only retention override in the repository is a test, and the binding chain (default policy → oversize throw → `Migration stopped because its backup failed` → Host exits before serving) is verified end to end, including the fact that no client diagnosis or CLI/desktop flag can escape it. The concern is therefore not moot, and it is not a documented deliberate boundary — README presents 512 MiB purely as a retention budget while the code makes it an admission-control limit on both migration and upgrade. I reduce severity only because the trigger requires an unusually large live database and the refusal itself is intentional and test-pinned, not because the failure mode is in doubt.
