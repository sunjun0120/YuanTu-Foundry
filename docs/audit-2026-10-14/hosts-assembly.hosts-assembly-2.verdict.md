### hosts-assembly-2 | confirmed | medium

**Checks:**

- `apps/agent-host/carrier.ts:107-120` — the second-connection handler really is `candidate.write(JSON.stringify({id:null,error:{...}}) + '\n')` followed by `candidate.end()`, with no `.on('error', …)` anywhere on `candidate`. `createInterface` (and therefore its read side) is only created on the _served_ path at `carrier.ts:121-133`.
- Listener counts measured directly (`.scratch/audit/exp-listeners.mjs`): an accepted `net.Socket` has `listenerCount('error') === 0`; after `createInterface({input: socket})` it is `1`. So readline is exactly what protects the served socket, and the refusal socket has no protection — the finding's key claim is correct.
- Real Host, not a replica: `apps/agent-host/main.ts` spawned with `--workspace … --listen 127.0.0.1:0` (`.scratch/audit/exp-verify-host2.mjs` / `host2b.mjs`). Client #1 connected and got a reply, then client #2 connected and was closed without reading. Host stderr: `node:events:487 throw er; // Unhandled 'error' event … Error: read ECONNRESET … TCP.onStreamRead`, exit code `1`, i.e. the default uncaught-error path. Identical for `resetAndDestroy()` and `destroy()`. A second connection that _does_ read the refusal frame leaves the Host alive (`AFTER_2500MS exit=null`), so the trigger is precisely "closed before the refusal payload is read".
- Isolation control: resetting the **first** (readline-wrapped) socket does _not_ produce an unhandled error — it surfaces as a rejected async iteration caught by `serveHost`'s `try` (`apps/agent-host/lifecycle.ts:84-101`), printed through `main.ts:88-90` as `read ECONNRESET`, and exits 1 via the teardown path. The hard crash is therefore specific to the refusal socket, as claimed.
- `apps/agent-host/lifecycle.ts:84-101` — the `try` covers `attach()` plus the `for await` loop; a socket `'error'` emission from the event loop cannot be delivered to it. No `uncaughtException` handler exists anywhere in the repo (grep over all files: only test-local `unhandledRejection` listeners), and `apps/web/main.ts:154` shows the web bridge does guard its sockets (`socket.on('error', …)`), so the omission is not a project-wide convention.
- Reachability: the socket carrier is a documented, user-facing mode (`README.md:529` "在 stdin/stdout 或 TCP 上提供 JSONL JSON-RPC", `README.md:545`, `apps/agent-host/cli.ts:15`), but **no shipped code passes `--listen`** — grep finds it only in `apps/shared/args.ts`, the Host help text, `README.md` and tests. The desktop spawns the Host over stdio (`packages/client/host-transport.ts:224-236`, `spawn(..., [hostPath, ...(options.args ?? [])])`), so the affected carrier is opt-in.
- `README.md:545` documents the intended behaviour of this exact path — "第二个连接会收到明确的拒绝报文后被关闭" (the second connection receives an explicit refusal frame and is closed) — and `README.md:713-737` lists no boundary covering a transport error killing the process. The code fails the boundary it documents, so this is not a deliberate tradeoff.
- Mitigation checked: `apps/agent-host/services.ts:42-55` already treats an abrupt death as a case the store must survive (`store.close()` is explicitly teardown-only, and `reconcileInterruptedRuns`/`recoverInterruptedStreams`/`resumableTasks` converge the log on the next start), so durable session state is not lost.

**Corrections:**

- Overstated impact: "the desktop's supervised carrier would then spend its three restart attempts" is wrong. The desktop's carrier is `stdioTransport` (`packages/client/host-transport.ts:224-236`) with no `--listen` argument, and nothing shipped passes `--listen`; that sentence should be dropped. The crash affects only a Host started manually with `--listen` (which the docs do recommend for serving externally, so the bug is still real, just not on the default desktop path).
- Severity `high` → `medium`: the trigger is trivial and the mode is documented, but it is a non-default carrier, the durable damage is bounded by existing reconciliation (`services.ts:42-55`), and no data or credential is exposed. It is an availability bug, not a data-integrity one.
- The cited range `carrier.ts:107-120` is accurate to within a line (the handler body is 108-119), and `lifecycle.ts:84-101` is exactly the `try` block — no line-number errors to correct. The stated "no process-level `uncaughtException` handler" claim was re-verified and holds.

**Reasoning:** I reproduced the exact three calls on the real Host and got `Unhandled 'error' event … ECONNRESET` with exit code 1, deterministic under both an abortive reset and a plain destroy, while a peer that reads the refusal leaves the process running; the served socket is protected solely because readline attaches the one `'error'` listener. The crash is an uncaught event-loop error, so it cannot reach `serveHost`'s `try` and the ordered teardown at `lifecycle.ts:102-135` does not run. The finding stands as written; the only substantive correction is that the desktop product cannot reach it because it never uses the socket carrier.
