**Corrections:**

- Severity medium → **low**. The code facts are right, but every shipped path is capped before the Host sees it: the only carrier the desktop uses is stdio fed by a client that always newline-terminates and locally rejects >16 MB, so the desktop client cannot reach the gap. Triggering it requires the documented-but-secondary `--listen` deployment plus a hostile or buggy peer, and it also presumes finding 1's unauthenticated listener. This is memory-exhaustion DoS on top of an input cap the peer could not otherwise exceed — it grants no capability the peer did not already have.
- "no bound in either direction" overstates the input half: growth is capped by V8's max string length and ends in a thrown `RangeError: Invalid string length` from readline's data handler (uncaught ⇒ Host dies, skipping teardown). Sharper failure mode, same trigger.
- The output half is code-accurate but unsupported by any demonstrated failure: the desktop drains stdout continuously (`host-transport.ts:146`, `:186`), and `packages/client/host-client.ts:457-458` records "a refused write (`false`) is backpressure, not failure: the transport buffers" as the intended design. A stalled consumer is theoretical here.
- Not documented as a deliberate boundary: I read `README.md:713-736` (已知边界) and found no framing/backpressure item, so this is not a "documented tradeoff" case.

**Reasoning:** The finding's mechanics are exactly as described — readline is unbounded on both carriers, the 16 MB cap only runs on an assembled line, and write results are discarded — and I reproduced unbounded in-process accumulation (63 MB of heap for 64 MB with no newline, source not paused) plus the V8 string-length throw it must eventually hit. What the finding overstates is reachability: the shipped Electron product spawns its Host over stdio from a client that newline-terminates every frame and rejects >16 MB before writing, so the only way in is the `--listen` carrier (or an embedding client) with a non-conforming peer, which the finding itself concedes depends on the unauthenticated-listener issue. That makes the real consequence a narrow availability concern in a non-default deployment rather than a reliability gap in the shipped carrier, hence low.
