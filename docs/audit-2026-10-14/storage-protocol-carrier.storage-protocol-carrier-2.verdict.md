**Corrections:**

- Line citations are accurate, with one truncation: the `session.delete` handler runs to line 143, not 139 — immaterial, the point (no workspace step) holds.
- "re-validated with a `git` call on every Host startup" understates the cost: one `validate` is ~10 git subprocess invocations, run sequentially per orphaned binding.
- "its only removal path, `removeOwned`" is slightly imprecise: `reconcile` also transitions `preparing` rows to `removed` (`manager.ts:513-524`). That path cannot apply to a delegated child's binding (state `ready`, directory present), so the conclusion is unaffected.
- The finding omits a partial mitigation that is worth stating: the directory _can_ be reclaimed by hand (`git worktree remove --force`), but doing so only converts the row to `blocked` (`manager.ts:471-478`), which then remains in the `['ready','blocked']` reconcile loop and is re-validated with a diagnostic on every subsequent startup — so "the product can never converge it" is right, "the user has no escape" would have been overstated.
- Severity kept at **medium** but at the low end: no data loss, crash, correctness or security consequence; the cost is disk (≤256 MiB per orphaned delegation, cumulative and invisible in the UI) plus git spawns at startup.

**Reasoning:**
Every cited mechanism checks out against the source: the SET NULL is enforced, `deleteSessionRows` never touches `workspace_bindings`, `resolve` throws on a deleted session before reading the row, and no RPC, UI command or reconcile branch can name or converge a `ready` binding whose `session_id` is null. Nothing in the shipped desktop path (all of these handlers and the carrier service are the live Electron-host path, not paused code) archives or removes a child's worktree when its run ends or when the conversation is deleted, and README's isolation section documents no such boundary, so this is a genuine gap rather than a documented tradeoff. It is a real but resource-only leak — unreclaimable through the product, silent, and bounded at ~256 MiB per orphan — which fits medium at its lower end rather than high.
