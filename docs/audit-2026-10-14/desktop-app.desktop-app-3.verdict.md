**Corrections:**

- The tooltip claim is narrower than written. Only a **root-level** entry has `path === name`; a nested `工具` is `sub/工具` (`files.ts:53`), which is not an exact dictionary key and is therefore left alone. So the "true path" tooltip is corrupted only in the top-level case, not generally.
- The `任务` example is right but for a reason the finding does not state: the word has two dictionary definitions, and insertion order makes `Tasks` (`:757`) shadow `Task` (`:615`) in the reverse index.
- The smoke's blindness is understated in one respect and overstated in another. `SCAN` does read attributes, so it would catch a Chinese name left untranslated — but it only hunts for _Han_, so a Chinese fixture name silently rewritten to English would pass even with Chinese fixtures. The real gap is the assertion's direction, not just the ASCII fixtures.
- Everything else in the evidence (line numbers, quotes, file/line citations, severity, "switching back restores") matched the source; `originals`/`applied` at `i18n.ts:1069-1070,1100-1102` plus the `zh-CN` early return at `:1073` do restore the on-disk name on switching back.

**Reasoning:** Every cited line contains exactly what the finding claims, and the data path is genuinely reachable in the shipped desktop renderer: a workspace entry name or a model-generated session title that equals a whole dictionary Chinese string is displayed (and tooltipped, at the root) under a name that does not exist on disk, with the walker offering no way to exempt data containers. The impact is bounded by the exact-match requirement and is fully reversible on switching back to `zh-CN`, so `low` is the right severity — the finding's own rating. The only real inaccuracies are the scope of the tooltip corruption (root-level only) and the unstated reason `任务` resolves to `Tasks`; neither changes the verdict.
