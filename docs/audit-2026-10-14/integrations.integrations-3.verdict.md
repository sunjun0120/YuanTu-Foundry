**Corrections:**

- Severity: **medium → low.** Both consequences need the _configured_ endpoint itself to misbehave, and that endpoint already receives the credential on the initial request. The redirect adds disclosure to a _second_ origin (compromise, open-redirect bug, or a canonical-host hop such as `api.gateway.example` → `gateway.example`), not first disclosure of the key. The unbounded body is likewise a DoS by the configured endpoint, which could equally just misbehave in other ways.
- The impact statement "a configured base URL … can answer 302 and receive the API key" overstates reach: the leak is protocol-specific. I verified `authorization: Bearer …` is stripped by undici cross-origin, so only `anthropic`-protocol connections leak (`x-api-key`); `openai`/`openai-responses` do not.
- The "unbounded body in the CLI/desktop main process" framing omits that the shipped desktop caller bounds the entire operation — including the body read — at 15,000 ms (`apps/desktop/main.ts:999`). I verified that bound bites mid-body: a server that sent `200` + an endless body made `discoverModels` reject at 504 ms under a 500 ms signal. So the desktop exposure is "up to 15 s of streaming at line rate" (hundreds of MB on a fast link), not an unbounded wait; only the paused CLI caller has no bound at all.
- "nothing in the returned `DiscoveryResult` records that the answering host differed … beyond the reported URL" is wrong in the code's favour: `endpoint` is the _requested_ URL (`discovery.ts:203,240`), so the result records nothing whatsoever about the answering host — the finding understates this rather than overstating it.
- Not reflected in the original: the docs assert the exact invariant the code breaks (`README.md:132`), which is additional support, not a mitigation.

**Reasoning:**
The code facts and the empirical behaviour are exactly as the finding describes: the explicit catalogue probe follows redirects by default, keeps the Anthropic `x-api-key` across a cross-origin hop (verified against the vendored undici's header-stripping list at `index.js:1309-1322` and end-to-end on Node 24.19.0), and reads the 200 body without the 1 MiB cap its automatic sibling applies — so the finding survives every refutation attempt and is not a documented tradeoff. The genuine weakness in the write-up is impact, not evidence: the redirecting party is the endpoint the operator already handed the key to, the leak is limited to the `anthropic` protocol, and the shipped caller's 15 s signal does bound the body read, leaving a defense-in-depth/origin-containment gap rather than a directly exploitable credential theft. That makes it a real but low-severity hardening issue; medium would require a path where the base URL is attacker-influenced, and no such caller exists (the two explicit callers take operator-supplied config only).
