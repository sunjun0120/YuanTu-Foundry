**Corrections:**

- The headline scenario is mis-attributed. On the shipped desktop a user cannot "cancel" a manual compaction at all: `session.running` is false (manual compaction is refused while a run is active, `compaction.ts:27`), so the composer button is a send button, and even the carrier `cancel` command would hit `this.aborter?.abort()` on a `null` aborter and send nothing. `{cancelled:false}` is what a **raw protocol client** (SDK/ACP/tests) gets, not what the desktop user sees. The defect is the same or slightly worse (no cancel handle anywhere), but the stated reproduction is wrong.
- Minor line error: the discarded `onCompaction` callback is `compaction.ts:127`, not `:126` (`:126` is `onUsage`).
- Loose citation: `dispatch.ts:38-49` is the handler-aggregation table, not the cancellation surface; the only cancellation method lives in `packages/protocol/rpc.ts:490` and is implemented at `handlers/runs.ts:57-72`. README.md:535 does list it.
- Severity stays **low**: the exposure is bounded by `summaryTimeoutMs` (120 s) and by one summary request's cost; no data loss, no corruption, and the shutdown path does abort the compaction. The actionable part is the missing handle plus the client-visible `cancelled:false`, not any unbounded spend.

**Reasoning:**
Every load-bearing code fact checks out: `manualCompaction` is created in the handler, aborted only in `lifecycle.ts:27`, and `run.cancel` can therefore only answer `cancelled:false` while the summary request runs to completion or to the 120 s deadline, with `ctx.restoring` blocking other mutating methods in the meantime. The finding overstates nothing about the mechanism but slightly misplaces the trigger, since the shipped desktop UI never sends `run.cancel` outside a run and would instead silently do nothing. That is a real correctness/UX gap with a bounded cost, so the original `low` severity stands.
