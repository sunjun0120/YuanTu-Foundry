## CAPABILITIES

- **Three model adapters, one SSE reader.** `AnthropicProvider`, `OpenAIProvider`, `ResponsesProvider` all stream through `readSse`, which bounds **one in-flight frame at 16,000,000 bytes** (completed frames are discarded, so the cap is not cumulative), uses a default idle timeout of **300,000 ms** (`packages/providers/sse.ts:6,15,71,96`), and closes a connect that produces nothing within **300,000 ms** (`packages/providers/http.ts:142-155`). HTTP error bodies are read for at most **2,000 ms / 4,096 chars**, and the endpoint's message is truncated to **2,048 chars** with `Bearer …`/`sk-…`/control-character scrubbing before it reaches any log (`packages/providers/http.ts:9-10,94-100`).
- **Endpoint URL validation is uniform except for discovery.** All three adapters reject a base URL carrying credentials, a query or a fragment, and refuse `http:` unless the host is exactly `localhost`, `127.0.0.1` or `[::1]`; each request sets `redirect: 'error'` (`packages/providers/anthropic.ts:82-93,126`, `openai.ts:27-41,122`, `responses.ts:52-68,150`). `packages/providers/discovery.ts` does neither (see integrations-3).
- **Prompt caching is four modes, not a switch.** `auto|blocks|key-only|off` with `0/false→off` and `1/true→auto` aliases (`packages/protocol/cache-modes.ts:19,29-34`); `auto` resolves per protocol (`anthropic` → block breakpoints, `openai*` → `prompt_cache_key`, anything else → nothing) (`cache-modes.ts:49-62`, `packages/providers/cache.ts:23-27`); the key is `sha256(protocol, model, system, JSON(tools))` truncated to **40 hex chars** and is computed per request, not per run (`packages/core/cache-key.ts:20-34`); an absent key disables cache fields entirely (`cache.ts:35-41`).
- **Usage is taken only from reported fields, never inferred.** Anthropic sums `input_tokens + cache_creation + cache_read` (`packages/providers/anthropic.ts:207-217`); the OpenAI chat adapter clamps cached tokens to `min(cached, prompt_tokens)` and **throws** if the endpoint omits `usage` (`openai.ts:211-218,320-321`); non-integer or negative token counts raise rather than being coerced (`anthropic.ts:26-30`, `openai.ts:18-22`, `responses.ts:18-22`).
- **Capacity comes from exactly three sources in a fixed order: declared → per-route map → catalogue.** The built-in `KNOWN_CAPACITY` table holds **one** entry (`api.deepseek.com`, prefix `deepseek`, 1,000,000 context / 384,000 output, `packages/providers/capacity.ts:49-57`); nothing is guessed for other routes (`capacity.ts:152-175`). Automatic discovery caches at most **32 routes** for **300,000 ms** on success and **30,000 ms** on failure, caps the catalogue body at **1 MiB**, times out at **3,000 ms** and keeps the first **1,000** models (`packages/providers/automatic-capacity.ts:21,36,66,81-82`).
- **Credentials:** environment first, then `~/.yuantu/credentials.json` (or `YUANTU_CREDENTIALS_FILE`, which must be absolute) (`packages/providers/credentials.ts:67-102`). Writes are temp-file + `rename` with the temp created `0600` via flag `wx` inside a `0700` directory; a key containing a control character is refused at write _and_ at connection build (`credentials.ts:25,37-43,115-145`). On Windows the comment concedes the mode protects only the read-only bit (`credentials.ts:111-113`).
- **MCP configuration bounds:** ≤16 servers, ≤32 KiB per file, ≤32 env/header entries, ≤64 args, ≤4,096-char strings, no control characters, `cwd` must resolve inside the workspace, remote URLs must be HTTPS-or-loopback, any header whose name matches `authorization|cookie|key|token|secret|password|credential` must be a `${VAR}` placeholder (the sole exception being `Authorization: Bearer ${VAR}`), OAuth scopes ≤16 with a `[A-Za-z0-9._:/-]{1,128}` alphabet, `clientSecret` must be a placeholder, `redirectPort` bounded (`packages/mcp/config.ts:46,49-60,73-95,120,139-145,157-168`).
- **MCP runtime bounds and reconnection:** 64 tools / 128 resources / 64 templates / 128 prompts / 16 pages per read; 60,000 ms per request, 30,000 ms handshake and call timeouts, 5,000 ms close bound; server schemas are refused above 64 KiB / 32 depth / 2,048 nodes and `$async` is rejected before `ajv.compile`, with Ajv2020 selected by `$schema`; the tool catalogue is re-read only on `notifications/tools/list_changed` behind a generation counter, and SDK-level reconnection is disabled (`maxRetries: 0`) with failures backing off 2,000 ms → 60,000 ms (`packages/mcp/tools.ts:26-48,114-132,317-319,373-396,508-571`).
- **MCP transport trust:** stdio is refused unless the sandbox mode is `host`; HTTP/SSE go through `McpFetchPolicy`, which permits only the server origin plus authorization-server origins learned from `www-authenticate` or a `/.well-known/` body served by an already-trusted origin, rejects `redirect: 'error'` and any origin change per hop (`packages/mcp/tools.ts:230-236`; `packages/mcp/oauth.ts:309-345`). OAuth tokens are AES-256-GCM with the 32-byte key held in the OS keyring and only a UUID `.secret-key-id` on disk; the loopback callback binds `127.0.0.1`, requires the exact `/callback` path and a matching state, answers once, and defaults to a 300,000 ms authorization timeout (`oauth.ts:49,561-657`; `packages/mcp/secret-cipher.ts:24-29,78-103,171-195`).
- **LSP lifecycle:** one client per language for a single workspace, created per run and closed by the tool registry; initialize 20 s, request 15 s, diagnostics 3 s, shutdown 2 s, stderr kept to 8,000 bytes, 200 diagnostics/file, 2 MB document cap, 32 open documents. A `WorkspaceEdit` containing any `create`/`rename`/`delete` resource operation is refused **whole** (`packages/lsp/client.ts:29-46`; `packages/lsp/tools.ts:255-283`), and the remaining text edits are applied atomically through the file journal with a byte-for-byte re-check after approval (`tools.ts:294-330`; `packages/tools/file-mutation.ts:118-127,181-202`).
- **Search backend selection and asset trust:** ripgrep is used **only** for a case-sensitive literal, with a fixed argv and an explicit pre-admitted file list (never a directory walk); batches are ≤256 files and ≤16,000 argv UTF-16 units, one JSON event ≤2 MiB, exit 1 (no match) and exit 0 (match) are distinguished while any other exit marks the batch failed rather than empty (`packages/search/ripgrep.ts:61-66,111-118,208-224,385-398`). A binary is accepted only if it is a regular non-symlink file, its `realpath` is **outside** the workspace, and its SHA-256 equals the lock file's digest; `PATH` is never consulted (`packages/search/ripgrep-assets.ts:122-143`). The symbol index is a separate `.yuantu/search/index.sqlite` (schema version 1) that downgrades to memory when unusable, with every row carrying size, mtime and SHA-256 (`packages/search/store.ts:8,44,87-129`).
- **Office parsing is JS-only for XLSX and regex/zip based for PPTX:** 20 MB source cap, PPTX ≤200 slides with ≤2 MB slide XML and ≤60,000 chars of text, DOCX via mammoth, XLSX via SheetJS with `sheetRows: 31` and output sliced to 20,000 chars (`packages/office/tools.ts:25,33-70`; `packages/office/read.ts:23,39,44,50`). DOCX/PPTX creation and editing shell out to `powershell.exe -NoProfile -NonInteractive -File automation.ps1` with the operation serialized as JSON on stdin (no `Invoke-Expression`), macros disabled (`AutomationSecurity = 3`), 120,000 ms timeout, stdout/stderr tails of 4,096 chars (`packages/office/automation.ts:82-113,150`; `automation.ps1:5,14,47`).
- **Knowledge is FTS5 with quoted-term queries.** The index uses `unicode61` with insert/update/delete triggers; a query is tokenized to letters/digits/underscore, capped at 8 words, and each is wrapped in double quotes (with `"` doubled in the fallback), so FTS5 operators cannot be injected (`packages/knowledge/store.ts:118-125,309-312`). Pinned documents are limited to 64 files (`store.ts:212`) with the same path/extension/sensitive-name screening as the tools (`store.ts:58-85`), chunked at 1,600 chars per 1,400-char step (`store.ts:221-227`), and a refresh skips a document whose size and mtime are unchanged before deciding to re-read it (`store.ts:256-267`), with the result limit capped at 20 (`store.ts:306`).
- **Workspace isolation refuses by name rather than copying best-effort.** Managed worktrees live at `<repo>/.yuantu/worktrees/<id>` with an id matching `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`; removal is `git worktree remove --force` only after a frozen snapshot, a preserved-file assertion, a manifest fingerprint re-check, a removal record and a state guard, and the directory must be listed by Git itself (`packages/workspaces/manager.ts:642-743`; `packages/workspaces/git.ts:437-457`). Symbolic links, junctions, submodules, sparse checkouts, unmerged indexes and repository-tracked credential files block the freeze with a named failure (`packages/workspaces/snapshot.ts:31-32,181-195,316-380`).
- **Desktop upgrade verifies a checksum, not a signature.** Only a manually chosen `-setup.exe` is accepted; the sibling `<installer>.json` manifest must declare `format 1`, `application com.yuantu.agent`, `win32`/`x64` and a three-component version, and the installer's SHA-256 must match; staging re-verifies and copies into `userData/upgrades/<uuid>`; rollback requires `--offline` and re-verifies whole-file SHA-256 maps of the preserved software and settings trees before restoring (`packages/maintenance/desktop-upgrade.ts:114-138,148-159,181-188,289-352`; `apps/desktop/main.ts:117-178`).
- **External hooks are installed as ordinary pipeline hooks, grouped one registration per Claude event**, so ordering, timeouts (1,000–600,000 ms) and disposability come from the existing dispatch; exit 0 allows, exit 2 blocks with stderr as the reason, and any other non-zero code is reported as a broken hook rather than a refusal (`packages/resources/hook-bridge.ts:249-256,362-407`; `packages/resources/hook-config.ts:35-37,180-201`; `packages/protocol/settings.ts:364-367`).

## FINDINGS

### integrations-1 | high | security

**Title:** Workspace-declared hooks run commands with no approval, and two of the six events run them even in a read-only/plan run — contradicting the bridge's own stated gate
**Evidence:** `packages/resources/hook-bridge.ts:20-30` states the four gates, including "a planning or read-only run does not run them, because that run's promise is that nothing outside the process is affected". Four events honour it — `PreToolUse` (`hook-bridge.ts:112`), `PostToolUse` (`:132`), `UserPromptSubmit` (`:151`), `Stop` (`:171`) all begin with `if (…readOnly) return undefined` — but `case 'SessionStart'` (`hook-bridge.ts:185-196`) and `case 'SessionEnd'` (`:197-206`) call `run(...)` unconditionally, and their context types carry no `readOnly` field to check (`packages/protocol/tool-hooks.ts:10-15` and `16-19`, versus `:20-25` and `:28-36` which do). `runCommand` reaches `prepareSandbox(..., 'hook')` and `spawn(plan.executable, plan.args, …)` (`hook-bridge.ts:278-296`) — no permission check, no approval, no `Approval` record ever produced (contrast `packages/resources/extensions.ts:72-75`, where a project-declared command gets `permission: 'command'` and therefore an approval). The declarations come from the workspace itself: `.claude/settings.json` and `.yuantu/hooks.json` (`hook-config.ts:30-33`), and the setting is opt-**out** — `hookBridgeSettings` returns `enabled: parseSetting(env,'YUANTU_HOOK_BRIDGE') !== false` (`hook-config.ts:49-51,67-74`), the desktop never sets that variable (no match for `YUANTU_HOOK_BRIDGE` under `apps/`), and the bridge is installed unconditionally when enabled in `createTools` (`packages/tools/index.ts:179-191`), which is the shipped assembly path (`apps/shared/runtime.ts:291`).
**Impact:** Cloning a repository and opening it as a workspace is enough to execute its declared commands on the user's machine, in any permission preset (including the read-only `observe` preset, whose policy denies `command`/`write`/`external` at `apps/desktop/permission-settings.ts:14-22` — the bridge never consults that policy) and in plan mode, because `SessionStart` fires there. The residual confinement is only the `hook` sandbox, whose mode resolves from `YUANTU_SANDBOX` when no call policy is installed — hooks invoked from the agent loop run outside the tool-dispatch `AsyncLocalStorage` policy (`packages/tools/sandbox-provider.ts:144-167`; `packages/tools/registry.ts:506` is where the policy is installed), i.e. the `native` backend, which README.md:729 itself describes as a partial write boundary where reads outside the workspace and network are unrestricted on Windows. README.md:509-511 states the opposite security posture for the JS hook path ("cloning a repo would be enough to make its code execute" is the threat the rule exists to stop).
**Recommendation:** Either gate `SessionStart`/`SessionEnd` like the other four by adding a `readOnly` field to `SessionHookContext`/`SessionEndContext`, or state in the bridge's own comment that only tool-scoped events are skipped. Separately, make the hook bridge require an explicit per-workspace trust decision (or run hook commands through the same permission/approval path as `ext_*` commands) instead of an environment opt-out that no shipped entry point sets.
**Confidence:** high (code facts and the absence of any desktop-side opt-out); medium on the residual-exploitability judgement, which depends on the sandbox backend in force.

### integrations-2 | medium | security

**Title:** An LSP `WorkspaceEdit` preview reads its target files without workspace or symlink validation, so an in-workspace symlink discloses a file outside the workspace into the approval record
**Evidence:** `prepareWorkspaceEdit` resolves each edit's URI with `uriToPath` (`packages/lsp/protocol.ts:87-93`), then validates containment **textually** — `const relative = path.relative(workspace.root, target); if (relative === '' || relative.startsWith('..') || path.isAbsolute(relative)) throw …` — and immediately reads the file with `const before = await readMutationBytes(target)` (`packages/lsp/tools.ts:288-301`, reached from `lsp_code_action` at `:442` and `lsp_rename` at `:587`). `readMutationBytes` opens the path directly (`open(file, 'r')`) with no `O_NOFOLLOW` and no `Workspace.resolve` (`packages/tools/file-mutation.ts:27-41`), whereas every other file tool goes through `Workspace.resolve`, which rejects symlinks at each path component, refuses hidden/credential paths and re-checks `realpath` containment (`packages/tools/files.ts:129-169`). The current bytes are embedded in the preview (`prepareWorkspaceEdit` builds the `FileChange` from `before`), and `Approval.change` is persisted verbatim into the session event log at `approval.required` (`packages/protocol/index.ts:235-241`; `packages/core/run-interaction.ts:68,76-77`).
**Impact:** A language server that reports an edit for a workspace-internal symlink (a path that is trivially present in real repositories — `node_modules/.bin/*` on POSIX, or any repo that vendors a link) makes the tool read the link target outside the workspace and write its contents into the approval preview and the session database, before anything is refused. The mutation itself is then blocked (the write path re-resolves through `Workspace.resolve` and rejects the symlink), so the failure is silent disclosure rather than corruption — and it is disclosure of exactly the files the workspace policy exists to protect (`~/.ssh/…` reachable through a link).
**Recommendation:** Resolve every edit target through `workspace.resolve(relative)` (or `realpath` + containment) before `readMutationBytes`, and treat a symlink or a canonical path outside the workspace as the same `outside` failure the textual check already produces.
**Confidence:** high on the code path; medium on how often a real server emits such a URI.

### integrations-3 | medium | security

**Title:** `discoverModels` follows redirects and reads an unbounded body, and `x-api-key` survives a cross-origin redirect
**Evidence:** `discoverModels` calls `fetchImpl(modelsUrl(config), { headers: discoveryHeaders(config), … })` with only a `signal` — no `redirect` option — and then `response.json()` unbounded (`packages/providers/discovery.ts:199-216`). Its two production callers that do not inject a fetch inherit that: the CLI `models` command (`apps/cli/main.ts:284-285`) and the desktop settings "read models" action, which passes a signal only (`apps/desktop/main.ts:998-1000`). Every other outbound model request in the codebase sets `redirect: 'error'` (`anthropic.ts:126`, `openai.ts:122`, `responses.ts:150`) and the auto-discovery wrapper does too, adding a 1 MiB body cap that the explicit path lacks (`packages/providers/automatic-capacity.ts:42-64`). `packages/tools/web.ts:10` records the project's own position: "`redirect: 'follow'` is not safe". In the vendored undici this checkout runs on, a cross-origin redirect deletes only `authorization`, `proxy-authorization`, `cookie` and `host` — custom headers are kept (`node_modules/undici/lib/web/fetch/index.js:1309-1322`), and the anthropic protocol authenticates with `x-api-key` (`discovery.ts:103-107`, asserted by `tests/models-discovery.test.ts:185-190`).
**Impact:** A configured base URL (or anything able to answer for it — a gateway, a corporate proxy, a plaintext hop) can answer `302` and receive the API key on every catalogue read, and can return an arbitrarily large body that the CLI/desktop main process buffers in full, unlike the identical call made by the automatic path. The failure is silent: nothing in the returned `DiscoveryResult` records that the answering host differed from the configured endpoint beyond the reported URL.
**Recommendation:** Pass `redirect: 'error'` (or re-validate each hop by hand the way `packages/tools/web.ts:179` does) and reuse the 1 MiB body cap for the explicit discovery path.
**Confidence:** high.

### integrations-4 | medium | security

**Title:** Office parsers have no decompression bound, so the size limits are checked only after an untrusted OOXML package has been inflated
**Evidence:** Every office reader caps the **input** and then hands the bytes to a parser that fully inflates entries before any output check runs. `inspect` reads the file and rejects only `> 20_000_000` bytes before `mammoth.extractRawText({ buffer: bytes })` for DOCX (`packages/office/tools.ts:32-37`) and `XLSX.read(bytes, …)` for XLSX (`:46`); the PPTX path inflates a slide and _then_ tests `xml.length > 2_000_000` (`packages/office/read.ts:43-46`), and the XLSX edit path inflates a worksheet and _then_ tests `xml.length > 10_000_000` (`packages/office/spreadsheet.ts:45-46`). `JSZip.loadAsync` itself imposes no output cap — its length probe only compares the inflated length against the header-declared `uncompressedSize` after the fact (jszip 3.10.2, `lib/compressedObject.js`), and the 20 MB input cap bounds the _compressed_ size only.
**Impact:** A crafted DOCX/XLSX/PPTX of a few hundred KB (well under every input limit) inflates to gigabytes inside the host process, which on the desktop is also the session-database writer; the observable cost is an unbounded memory spike and an out-of-memory abort or a tool failure that names the wrong cause, reached from an ordinary `office_inspect` call on a file the model was simply asked to read. The failure is reachable with a document whose declared entry size alone is enough to make the post-inflate check useless.
**Recommendation:** Sum the central-directory `uncompressedSize` values and refuse a package whose total or per-entry declared size exceeds a bound (the existing 2 MB / 10 MB / 20 MB budgets) _before_ calling `async('string')`, and cap mammoth/SheetJS by the same declared-size check rather than by the compressed input length.
**Confidence:** high on where the checks sit; medium on the exact allocator outcome (JSZip throws a `RangeError`/aborts depending on the inflated size and platform).

### integrations-5 | low | correctness

**Title:** A content-filtered response is reported as a clean `stop` by the chat adapter and as a token-length truncation by the Responses adapter
**Evidence:** `packages/providers/openai.ts:306-313` maps `finish_reason === 'content_filter'` into `finishReason: 'stop'`, so a filtered (and typically empty) turn is indistinguishable from a completed answer. `packages/providers/responses.ts:224-231` maps any `response.incomplete` terminal to `finishReason: 'length'` and never reads `incomplete_details.reason`, which is where the endpoint distinguishes `max_output_tokens` from `content_filter`. The core acts on both labels: `'stop'` with no content falls into the empty-response retry path (`packages/core/agent.ts:2750-2759`), and `'length'` produces the "N/M output tokens" truncation report and marks the message interrupted (`agent.ts:2831-2875`) and is also the trigger for shrinking and retrying a summary (`packages/core/context.ts:948-964`).
**Impact:** A refusal that comes from the provider's content filter is misreported in both directions: the chat path re-sends a request that will be filtered again (spending tokens on a retry loop bounded only by the retry budget) while telling the operator "empty response", and the Responses path tells the operator the answer was cut off at the output-token limit and may pay for a summary re-generation, when neither was the cause.
**Recommendation:** Carry the filter outcome explicitly (the adapters already have a `truncation`/diagnostic channel) and let the run report "the endpoint filtered this answer" instead of mapping it onto `stop` or `length`; `responses.ts` should read `incomplete_details.reason` before choosing.
**Confidence:** high on the mappings; medium on how often the retry/compaction branches actually fire for a filtered turn.
