**Corrections:**

- Severity should be **medium**, not high. The consequence is exclusively a silent loss of an optimization: `packages/tools/search-backend.ts:45` routes every search to `input.fallback(...)`, the built-in streaming scanner, which is the documented supported configuration (`README.md:728`: "没有可用资产、或执行环境无法安全启动进程时，一律回退内置流式扫描，不回退 host 进程"). No crash, no data loss, no security regression, and `README.md:725-726` still makes the built-in scanner report its coverage honestly, so results stay correct. The measurable costs are one unread lock lookup per host process (memoised at `search-backend.ts:33-37`) plus ~5 MB of shipped dead weight in the installer.
- The finding understates the blast radius rather than overstating it: the same `dist/build` lookup breaks the running-from-`dist` development/CLI layout too, not just the packaged installer. That argues for keeping the finding, not against it, but "packaged desktop can never use it" is narrower than reality.
- The recommendation is sound; "high" confidence in the finding's own evidence is warranted.

**Reasoning:**
I reproduced the failure twice from the real compiled artifact (with and without a staged asset at the exact `extraResources` destination) and proved the lock alone is missing by injecting it, after which the identical staged `rg.exe` resolved to the digest pinned in `build/search-assets.lock.json:9`. `rootDir: "."` in `tsconfig.build.json` really does push the module from `packages/search/` to `dist/packages/search/`, and nothing in the packaging pipeline ever stages `search-assets.lock.json`, so `buildRoot()` pointing at `dist/build` can only ever yield `null` in a shipped build. The reason this survives every gate is that the one test that exercises the real asset (`tests/search-ripgrep.test.ts:274`) runs under the source layout, where the lookup succeeds. The code really does what the finding says and the consequence is real, but it is a silent performance/feature regression with a safe documented fallback, so "high" is too strong.
