## CAPABILITIES

- Test entry point is `scripts/run-tests.mjs`; discovery is exactly the top-level `tests/*.test.ts` set (`scripts/test-execution-policy.ts:89-95`) — 222 files today — and the default schedule is serial at `--test-concurrency=1` (`scripts/run-tests.mjs:27-28,112-124`).
- `--schedule=partitioned` starts a parallel phase (default `--parallel-concurrency=2`) and then the serial phase; a phase whose exit code is non-zero stops the next phase (`scripts/run-tests.mjs:141-159`), and an empty phase is not started at all (`:148`).
- Phase completeness is enforced from the report, not from the child's status: each phase must write an NDJSON report containing both a `phase-summary` and a `run-summary`, and a missing, unparsable or non-terminal report is a failed run (`scripts/run-tests.mjs:218-232,251-273`).
- Exit code of the runner is the child's exit code in the serial path (`:134`) and 1 in the partitioned path when any phase failed or any report was incomplete (`:171`).
- `--plan` requires `--schedule=partitioned`, prints the partition and exits 0 without creating a log directory; `--concurrency` is refused together with the partitioned schedule (`scripts/run-tests.mjs:64-69,94-104`).
- `--timings=<path>` merges the verified per-phase records and writes `<path>.meta.json` carrying command, node version, git HEAD, dirty-file count, schedule, phase walls and whole-run wall clock (`scripts/run-tests.mjs:239-299`).
- `test-parallel-safe.json` holds 16 entries, each with a reason and the SHA-256 of the test file plus every reviewed input; an entry is only in the parallel phase while every input still hashes (`scripts/test-execution-policy.ts:212-246`). All 16 entries currently hash-match, and each entry's input list is a superset of its test's transitive local-import closure (measured by BFS over local import specifiers).
- Policy validation is fatal rather than advisory: version must be 1, entries must name discovered top-level test files exactly once, `inputs` must be non-empty, include the test file itself, use lowercase 64-hex digests and stay inside the repository (`scripts/test-execution-policy.ts:108-181`); an absent policy file means everything is serial (`:193`).
- Skips are carried separately from passes in every summary: Node's own counts plus a `SKIP <name>: <reason>` line per skipped case (`scripts/test-summary.mjs:6-13`), and the runner prints `tests/pass/fail/skip/cancelled/todo` per phase (`scripts/run-tests.mjs:306-319`).
- `npm run check` is `format:check → docs:check → references:check → i18n:check → typecheck → test → build → smoke:client` (`package.json:57`); `bench:check` and `coverage` are separate CI jobs that `needs: check` (`.github/workflows/ci.yml:47-76`).
- `typecheck` covers only `packages/**/*.ts`, `apps/**/*.ts` and `tests/**/*.ts` (`tsconfig.json:19`, `package.json:43`); `scripts/**/*.ts` and `benchmarks/**/*.ts` are outside it.
- `docs/` is empty and both documentation gates treat that as valid (`scripts/docs-facts.mjs:286-292`, `scripts/check-references.mjs:153-163`). `docs:check` recomputes the README's two generated blocks from code and rejects a table of dated-stale claims (`scripts/docs-facts.mjs:256-273,312-345`); `references:check` resolves backticked repository paths in README, `docs/*.md`, `.github/workflows/*.yml` and every `package.json` script value, plus markdown link targets and anchors, with `ALLOWED_MISSING` deliberately empty (`scripts/check-references.mjs:54,121-148,171-193`).
- `i18n:check` scans `apps/desktop/**/*.ts` (four reasoned exceptions, each required to still match a file), `packages/carrier/**` and `*worker*.ts` under `packages/tools` and `packages/mcp`, with comments stripped first (`scripts/i18n-gate.mjs:90-130,156-203`).
- CI platforms: `check`, `bench` and `coverage` run on `ubuntu-latest` with `YUANTU_SANDBOX=host`; `desktop-smoke` on `windows-latest` runs the Windows sandbox acceptance plus 15 named test files, `cargo test` for the AppContainer helper and `smoke:desktop`; `native-macos` runs the Seatbelt probe, 9 named files and `package:macos:dir` (`.github/workflows/ci.yml:22-122`). ## FINDINGS

### build-ci-tests-1 | high | correctness

**Title:** The packaged desktop can never use the ripgrep binary it ships: the lock file the runtime verifies against is looked up relative to the compiled module and is not in the package.
**Evidence:** `packages/search/ripgrep-assets.ts:43-45` computes `buildRoot()` as `new URL('../../build', import.meta.url)`; `:75-77` defaults the lock to `<buildRoot>/search-assets.lock.json`; `:94-104` returns `null` from `resolveSearchBinary` whenever that lock is `null`; and `:60-66` can only reach `process.resourcesPath/search-assets/<version>/<key>` via `lock.version`. In the source layout the module sits at `packages/search/`, but the shipped host imports the compiled `packages/search/ripgrep-assets.js`, one level deeper under `dist/`: importing the current build (`dist/packages/search/ripgrep-assets.js`) yields `buildRoot() = E:\agent-desktop\YuanTu-Foundry\dist\build`, and no `search-assets.lock.json` exists there (`dist/build` does not exist at all). `electron-builder.config.cjs:10-24` ships only `dist/apps`, `dist/desktop`, `dist/packages`, `dist/program-runner`, `package.json` and `LICENSE`, and `:25-36` stages only `runtime` and `search-assets` into `resources` — no `build/` directory and no lock. Reproduced with the staged asset present at exactly the path `extraResources` creates (`.scratch/audit/fake-resources/search-assets/15.2.0/win32-x64/rg.exe`, a copy of the real `build/search-assets/15.2.0/win32-x64/rg.exe`) and `process.resourcesPath` pointed at it: `loadSearchAssetLock()` → `null`, `resolveSearchBinary({workspaceRoot})` → `null`. `packages/tools/search-backend.ts:34-45` then reports the backend unavailable and calls `input.fallback(...)`, i.e. the built-in scanner, and `packages/tools/index.ts:110-112` wires that backend in by default.
**Impact:** in the shipped desktop the documented fast path (README.md:728: the digest-verified pinned ripgrep is used when the asset is present, and `copy-search-assets.mjs` puts it in the app resources) is inoperative: every `search_files` call silently uses the JavaScript scanner while the installer carries a ~5 MB `rg.exe` plus its license that can never execute. The failure is silent by design (a missing lock is not an error), so nothing in `check-windows-package.mjs` or the packaging scripts notices.
**Recommendation:** make the lock reachable from the packaged layout — stage it with the asset (`{ from: 'build/search-assets.lock.json', to: 'search-assets.lock.json' }` in `extraResources`, or copy it beside the binary in `copy-search-assets.mjs`) and have `loadSearchAssetLock()` also try `path.join(process.resourcesPath, 'search-assets.lock.json')`; then assert in `check-windows-package.mjs` (which already walks `resources/`) that the staged asset resolves for the packaged layout.
**Confidence:** high

### build-ci-tests-2 | medium | test-gap

**Title:** A test file that runs none of its tests is reported as one passing test, so a file that stops early is indistinguishable from a healthy one in every gate.
**Evidence:** Node's runner emits a file-level test node, and `scripts/test-timings.mjs:63-75` records every `test:pass`/`test:fail` as a `case` record — including that node — while only writing a `file-summary` for a per-file summary (`:87-97`). `scripts/run-tests.mjs:251-273` accepts a report on the presence of `phase-summary` + `run-summary` alone, and `:218-232` never compares the report against the files the phase was given. Measured on this tree: a file containing only `process.exit(0)` and a file with one passing test followed by `process.exit(0)` both produce exactly `case 1, run-summary {tests:1, passed:1, failed:0, skipped:0}` with **no** `file-summary`, and `node scripts/run-tests.mjs <file>` exits 0; a healthy single-file run produces `file-summary 1` and the real subtest count (10 for `tests/slots.test.ts`, 33 across three files). `scripts/check-windows-sandbox.mjs:29-33` guards only `tests >= 1 && passed === tests`, which the same synthetic file satisfies.
**Impact:** any change that makes a test file stop before its assertions — an early `process.exit(0)` in the file or in an in-process helper it calls, an emptied file, a renamed file that keeps its name, a worker killed with exit code 0 — keeps `npm run check`, `check:windows-sandbox` and the "nonempty passing run with no skips" acceptance green while those assertions never execute. The runner's stated invariant ("a missing or truncated report is a failed run rather than a successful one with less output", `scripts/run-tests.mjs:7-8`) does not cover a report that is present but describes fewer files than were requested.
**Recommendation:** in `verifyPhases`, require one `file-summary` record per requested file (rejecting a phase whose report names fewer files than it was given), and make `check-windows-sandbox.mjs` assert the same thing instead of relying on `tests >= 1`; a file-level `case` with no sibling `case` records for that file is worth refusing outright.
**Confidence:** high

### build-ci-tests-3 | medium | reliability

**Title:** `package:windows:protected` ends by hashing an installer name the protected build never produces.
**Evidence:** `package.json:18` chains `… electron-builder --config electron-builder.protected.config.cjs --win --x64 && node scripts/check-windows-package.mjs --production && node scripts/write-release-manifest.mjs`. `electron-builder.protected.config.cjs:47` sets `nsis.artifactName` to `YuanTu-Agent-${version}-windows-${arch}-protected-setup.${ext}`, and `node_modules/app-builder-lib/out/platformPackager.js:552` resolves target options before platform/config options, so that is the artifact name. `scripts/write-release-manifest.mjs:10` hardcodes `YuanTu-Agent-${pkg.version}-windows-x64-setup.exe` (the non-protected name from `electron-builder.config.cjs:108`) and `:11-13` hashes exactly that file.
**Impact:** the release gate documented at README.md:364 fails at its last step with ENOENT after the entire protected build and signature validation have run, leaving no checksum manifest; and because `dist/release` is reused, an unsigned installer of the same version left behind by an earlier `npm run package:windows` (README.md:56) makes the step succeed and write `<installer>.json` attesting a sha256/version for the wrong artifact.
**Recommendation:** pass the artifact path (or a glob match and its resolved name) into `write-release-manifest.mjs` so the protected and non-protected flows each attest the installer they just built, and record the file name that was hashed in the manifest.
**Confidence:** high

### build-ci-tests-5 | low | test-gap

**Title:** `npm run typecheck`, and therefore `npm run check`, does not type-check the TypeScript that implements the gates themselves.
**Evidence:** `tsconfig.json:19` includes only `packages/**/*.ts`, `apps/**/*.ts` and `tests/**/*.ts`, and `package.json:43` is `tsc --noEmit` against that config, so `scripts/test-execution-policy.ts`, `scripts/select-tests.ts` and the `benchmarks/**/*.ts` cases are never checked; `scripts/run-tests.mjs:19` imports the policy module through Node's type stripping, which erases types without checking them. I confirmed the omission is currently latent (not a live defect) by running `tsc --noEmit` with the repository's compiler options over `scripts/select-tests.ts`, `scripts/test-execution-policy.ts` and four `benchmarks/**/*.ts` files: no errors.
**Impact:** a type error introduced in the code that decides which tests run, or how they are partitioned, produces no signal from any gate; the only feedback is whichever test happens to exercise that module at runtime, and the benchmark paths have no such coverage.
**Recommendation:** add `scripts/**/*.ts` and `benchmarks/**/*.ts` to a typecheck program (either the root `include` or a second `tsc --noEmit -p` step in the `typecheck` script).
**Confidence:** high
