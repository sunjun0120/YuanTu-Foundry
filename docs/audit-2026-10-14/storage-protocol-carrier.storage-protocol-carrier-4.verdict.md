**Corrections:**

1. **The impact link to finding 1 is wrong and self-contradictory.** The 512 MiB cap is _not_ measured on the live file: `createBackup` VACUUMs into `stage` and then measures the stage (`database-maintenance.ts:341-344` → `inspectDatabase` returns `bytes: statSync(canonical).size`, `:301`), i.e. the compacted copy (probe: 100 MB source → 12 KB snapshot). Free pages therefore never count toward the migration-backup ceiling, so "the file can pass the 512 MiB migration-backup ceiling while the user's live data is well under it" cannot happen — finding 1 itself says the ceiling applies "after `VACUUM INTO`, so this is real content, not free pages". The disk-waste cost is real but it is _not_ a migration blocker.
2. **"Nothing in the product ever returns disk space to the filesystem" is overstated.** `restoreDatabase` (`database-maintenance.ts:498-509`) runs `VACUUM main INTO stage` on the chosen candidate and `renameSync(stage, target)`, i.e. it installs a freshly compacted file as the live database. Both halves are documented operator commands (`db-backup` at `:394-399`, reason `'manual'`, and `db-restore` at `apps/cli/main.ts:197-210`; manual backups are valid restore candidates per `listDatabaseBackups` `:432`). Backing up then restoring the just-taken snapshot reclaims the whole freelist without data loss whenever live data fits the 512 MiB cap. This is an undocumented two-command workaround rather than a compaction feature, so the gap the finding names (no explicit compaction; deletion reclaims nothing) still stands — but the absolute phrasing does not.
3. **Cost is bounded by the high-water mark, not cumulative.** With `auto_vacuum = 0` the freed pages stay on the freelist and are reused by later writes (`freelist_count` above), so waste equals the peak historical live size of the workspace DB, not the sum of deleted sessions. "sessions.sqlite only ever grows" is true of the byte count, but the practical cost does not grow with deletion count.
4. Minor citation imprecision: `database-maintenance.ts:258-303` is `registerDatabase`/`inspectDatabase`, not the maintenance surface; the surface is `:394`, `:444`, `:486`, `:528`. "no table is created with anything other than the default `auto_vacuum = 0`" is loose phrasing — `auto_vacuum` is a database-level pragma, not per-table — but the substance (nowhere set) is verified.

**Reasoning:** The finding's factual core survives every check I could apply: the connection and schema code never touches `auto_vacuum`, no product path executes a bare `VACUUM`, and an empirical probe shows a 100 MB sessions database stays 100 MB after every row is deleted. What does not survive is the claimed consequence: the migration-backup ceiling is applied to the compacted `VACUUM INTO` snapshot, so file bloat cannot block an upgrade, and backup-then-restore already installs a compacted file, so "nothing ever returns disk space" is too absolute. What remains is a genuine but bounded disk-hygiene gap — deleted conversations leave the workspace database at its peak size, with no advertised compaction command — which is correctly rated low.
