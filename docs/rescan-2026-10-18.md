## 5. 缺陷与优化项

### X-01（P1，已复现）`openBlobBatch.add()` 在 `git fast-import` 提前退出时永久挂起

**位置**：[git.ts](../packages/workspaces/git.ts) 的 `openBlobBatch`（约 609 行）、`write`（约 641 行）、`add`（约 656 行）。

**根因**：`write()` 在 `child.stdin.write()` 返回 `false` 时只等待 `drain` 或 `close`：

```ts
const write = async (chunk: Buffer | string) => {
  if (failure) throw failure;
  if (!child.stdin.write(chunk))
    await new Promise<void>((resolve) => {
      const done = () => {
        child.stdin.off('drain', done);
        child.off('close', done);
        resolve();
      };
      child.stdin.once('drain', done);
      child.once('close', done);
    });
  if (failure) throw failure;
};
```

如果子进程在 `add()` 之前或期间已经退出（不是 Git 仓库、磁盘满、对象库损坏、OOM），`close` 已经发生过，之后注册的 `once('close')` 不会再触发，`drain` 也不会来；`failure` 只在 spawn error、取消或 `abort()` 时设置，**收到非零退出码时不会设置**。`abort()` 只会 `child.kill()`，也不能唤醒这个 Promise。

**复现**：把 `openBlobBatch` 指向一个不是 Git 仓库的临时目录，调用 `add(Buffer.alloc(8 MiB))`，5 秒后仍未返回：

```text
add hung after 5s
```

扫描时新增的 [workspace-blob-batch.test.ts](../tests/workspace-blob-batch.test.ts) 覆盖了正常写入、空批次、取消与“来源抛错”，但没有覆盖 Git 提前退出，因此这条路径仍会漏过。

**影响**：`collectTreeBlobs`（结果导出）与 `buildTree`（冻结的 `writeBlobs`，约 673 行）都可能永远不返回。子代理结束时导出卡住，父运行也拿不到 `subagent.workspace` 帧；用户看到的是“子代理已完成但一直没有结果”。取消信号也解不开，因为挂起发生在 `write()` 内部，而不是 `finish()` 的 `closed` 等待。

**建议**：

- 在 `write()` 中同时观察 `closed` 与 `failure`，任一先到都结束等待；`closed` 非零时设置 `failure`。
- `add()` 在写入前后检查 `failure`，并在 `child.exitCode !== null` 时立即抛出带 stderr 的 `WorkspaceGitError`。
- 给整批写入一个总时限（不只 `finish()`），或让 `stop()` 同时把 `failure` 传播给所有等待者。
- 新增回归：在 `add()` 期间让 `fast-import` 以非零码退出，断言 `add()` 在 1 s 内 reject；取消同样要在 1 s 内 reject。

**验收**：Git 正常、Git 提前退出、取消、磁盘写失败四种路径都有超时上限；`freezeSnapshot` 与 `WorkspaceResultsService.export` 不会无限挂起；新增测试在 `--concurrency=1` 与默认并行下都稳定通过。

### X-02（P1，已复现）`.yuantu` 未写入 `.git/info/exclude`

**位置**：[snapshot.ts](../packages/workspaces/snapshot.ts) 的 `snapshotMetadataRoot`（约 181 行）把快照放在 `<repo>/.yuantu/workspace-snapshots/<id>`；工作树在 `<repo>/.yuantu/worktrees/<id>`；spill 在 `<repo>/.yuantu/spill`。产品代码中没有写入 `.git/info/exclude` 或 `core.excludesFile` 的路径（全仓搜索只有测试与基准手工写入，例如 [workspace-manager.test.ts](../tests/workspace-manager.test.ts) 第 83 行）。

**复现**：临时 Git 仓库不预置忽略规则，调用一次 `freezeSnapshot` 后：

```text
snapshot c2d7f69806154a442720f52deabe5fe6
status: ["?? .yuantu/",""]
untracked listed: 4 ['.yuantu/workspace-snapshots/.../files/...', ...]
```

连续冻结两个不同状态（40 个文件）后，未跟踪条目为 84 个，全部在 `.yuantu/` 下：

```json
{ "distinct": true, "untrackedTotal": 84, "untrackedYuantu": 84 }
```

**影响**：

1. 用户仓库的 `git status` 出现 `.yuantu/`；`git add -A` 或提交工具会把运行态一起提交。`.yuantu/spill` 保存的是完整工具输出（命令 stdout、文件内容），可能含密钥；`.yuantu/workspace-snapshots` 保存源码副本。这不是“看起来脏”，而是**把内部状态和潜在敏感内容写进用户版本库**的风险。
2. 冻结/搜索的 `git ls-files --others --exclude-standard` 会枚举这些副本。`walkWorkingTree` 在过滤 `.yuantu` 之前先执行 `paths.length > MAX_FILES`（约 413 行），所以长期使用后，`.yuantu` 里的副本会把“工作树文件数”推到 200,000 上限，导致**之后的所有冻结都失败**，直到用户手工删除 `.yuantu`。仓库越大、委派越多，越容易触发。
3. 即使没有触发上限，每次冻结的 `ls-files` 输出也会随快照数量线性膨胀，拖慢每一次委派。

**建议**：

- 在首次使用某个仓库时，向 `.git/info/exclude` 追加一行 `.yuantu/`（不存在才追加，保留原内容，原子写入；`.git` 是文件的工作树需要解析 `gitdir`）。这比改用户 `.gitignore` 更合适：它不进入提交，也不会把内部实现写进项目。
- `walkWorkingTree` 先过滤 runtime/credential 路径，再检查 `MAX_FILES` 与字节预算；上限只约束真正会被冻结的文件。
- 如果无法写 `.git/info/exclude`（只读仓库、权限不足），明确提示用户并继续，不要静默留下污染。

**验收**：没有忽略规则的新仓库冻结两次后 `git status --porcelain` 不出现 `.yuantu`；`git ls-files --others --exclude-standard` 不返回 `.yuantu`；在 `.yuantu` 中放入超过 200,000 个文件后仍能正常冻结（或者以“运行态不计入”为由拒绝，而不是报工作树文件超限）；已有 `.git/info/exclude` 内容不被破坏；只读仓库给出可见诊断。

```text
docs: 13
```

也就是说，**约 91% 的被枚举文件不是源码**。`search_files`、`list_files` 与符号索引（[service.ts](../packages/search/service.ts) 的 `symbols`/`reconcile`）都使用这份清单；`repo_map` 的启发式扫描却跳过 `dist/build/coverage`，两个工具对“工作区里有什么”给出不同答案。

**影响**：

- `search_files` 会扫描构建产物、测试日志与嵌套代理工作树，结果噪声大，也可能把 `.scratch` 里的临时密钥/日志带进模型上下文。
- 符号索引构建把生成代码/`.d.ts` 当成源码，产生重复声明；在命中 5 s 上限时标记 `partialFiles`/`time-limit`，`repo_map` 查询可能长期显示“索引不完整”。
- `list_files` 与 `repo_map` 的覆盖信息互相矛盾，模型可能据此判断“仓库里没有某个符号”。

**建议**：在 Git 工作树中直接用 `git ls-files --cached --others --exclude-standard -z` 作为 inventory 的来源（与冻结使用同一条真源），非 Git 目录再回退到 `readdir`；或者至少把 `repo-map` 的忽略集抽成共享策略并加入 `.next`、`target`、`out`、`.venv`、`.cache` 等常见构建目录。不要只扩大 `excluded` 名单——用户项目的构建目录名不可穷举，`.gitignore` 才是权威。

**验收**：夹具中放 `dist/`、`.scratch/`、`artifacts/`，`list_files`、`search_files`、`repo_map`（无 query 与有 query）默认都不返回它们；显式 `include` 可以覆盖；符号索引的 `filesConsidered` 与仓库真实源码数一致；本仓库的 inventory 从 29,581 降到约 2,000，耗时从约 5 s 降到百毫秒级。

### X-04（P2，已复现）工作区快照没有回收

**位置**：[snapshot.ts](../packages/workspaces/snapshot.ts) 的 `snapshotMetadataRoot`（约 181 行）按 `snapshotId` 建目录，`publishSnapshot` 把整份 manifest 与 `files/` 放在该目录下；[manager.ts](../packages/workspaces/manager.ts) 只删除工作树与绑定，不删除快照目录。

**复现**：40 个文件、两次不同冻结，`.yuantu` 下出现 84 个未跟踪条目（两套完整副本 + 元数据）。代码中没有任何 `rm` 指向 `workspace-snapshots`；全仓搜索 `workspace-snapshots` 只有写入与读取。

**影响**：

- 每个“内容不同”的快照都会保存一份完整树。一个 1 GB 的仓库，若在 10 个不同状态上委派，`.yuantu` 会多出约 10 GB；删除会话、归档/移除绑定、清理结果都不会回收它。
- 与 spill 不同（[spill.ts](../packages/tools/spill.ts) 有 1 GiB 总上限与 24 h 孤儿清理），快照既没有配额，也没有 UI 显示占用。用户只会在磁盘告警时发现。
- 快照按 `snapshotId` 分目录，跨快照不做内容去重；相同文件版本在多份快照里各存一份。

**建议**：把快照纳入与工作树相同的“可证明所有权 + 可恢复”回收模型：

1. 对 `workspace_snapshots` 表与 `workspace_bindings`/`workspace_results` 做引用计数，删除无引用且超过保留期的元数据目录；正在被 `applying` 的结果保留。
2. 增加显式维护入口（“设置 → 保留的工作区”已有面板，可加“快照占用/清理”），并在 Host 启动或空闲时做有上限的孤儿扫描。
3. 长期可以把 `files/` 提升为仓库级内容寻址存储（`blobs/<sha256>`），快照只存 manifest；这也能消除跨快照重复。先做回收，再做去重。

**验收**：冻结 A、修改、冻结 B、删除/归档对应绑定后，清理只释放 B 的元数据而不影响 A 的可恢复性；删除结果/会话不会留下不可达快照；配额与剩余空间可见；并发分配与清理不互相删除。

### X-05（P2，已实测）冻结仍按文件串行读取/暂存

**位置**：[snapshot.ts](../packages/workspaces/snapshot.ts) 的 `walkWorkingTree`（约 388 行）在 `for (const relative of paths)` 中逐文件 `await lstat` → `await readFile` → `await onFile`；`collectStagedTree`（约 520 行）在回调里逐文件 `await writeFile`。

**实测**：800 个 16 KiB 文件，`collectFileDigests` 348 ms、`collectStagedTree` 907 ms、`freezeSnapshot` 2,869 ms；2000 个文件冻结 5,702 ms。单文件约 2.9 ms；其中约 1.25 s 是两次逐文件读取/暂存，其余是建树、commit、发布与清理。

**影响**：委派前的冻结是用户可感知的等待；文件数多、单文件小（典型源码树）时最明显；网络盘/杀毒软件扫描下会进一步放大。

**建议**：

- 给 `walkWorkingTree` 的读取与 `collectStagedTree` 的写入加有界并发（与 `fillWorktree` 的 `FILL_CONCURRENCY = 8` 一致），保持结果按路径排序、错误时停止领取新文件、等在途操作结束后再抛。
- 或者把“读取 + 哈希 + 写暂存”合并成一次遍历，用暂存文件的内容计算 manifest；第二次遍历只用于稳定性校验（CAP-03），并按 stat 变化决定是否需要重读，保持“内容不同必须拒绝”的语义。
- 不要把并发开到无界：Windows 上同时打开数百个文件会适得其反。

**验收**：2000 文件冻结从 5.7 s 降到可接受范围（以同机基准为准，至少 2 倍改进）；CAP-03 的并发改写夹具仍拒绝；取消在 100 ms 内停止领取新文件；峰值 RSS 不高于当前 95 MiB 量级。

测量脚本 [worktree-fill.ts](../benchmarks/worktree-fill.ts) 目前是未跟踪文件，建议随本轮修复一起提交，否则下一位维护者没有同机对照入口。

### X-06（P3，已实测）结果导出仍遍历整树写 blob

**位置**：[snapshot.ts](../packages/workspaces/snapshot.ts) 的 `collectTreeBlobs`（约 545 行）；[results.ts](../packages/workspaces/results.ts) 的 `export`（约 170 行）先对 `executionRoot` 全树写 blob，再 `writeTree`/`diffTrees`，最后只读取差异文件。

**实测**：800 文件从 38.3 s 降到 0.39 s（批处理修复），但仍然是“整树读取 + 整树写对象”。子工作区通常只改少数文件。

**影响**：导出延迟随树大小线性增长；对 10,000 文件的仓库，即使只改 1 个文件，也要把 10,000 个文件读一遍并送入 blob 流（未变内容由 Git 按对象去重，但读取和哈希仍发生）。当前批处理把常数降下来了，但没有改变复杂度。

**建议**：以基线树为对照，先用 Git 的 diff 机制得到变更路径（例如在子工作区使用私有 index 或 `git diff --no-index` 的等价物），只对变更路径写 blob；或者在分配工作树时把基线树写入一个私有 index，结束时用 `git diff-index --cached` 得到差异。注意保持结果导出的完整性校验（路径、模式、UTF-8、大小限制）不依赖“整树已写”。

**验收**：10,000 文件、1 个改动的夹具导出时间与“改动数”相关而不是与“树大小”相关；未变更文件不产生新 blob；结果 digest 与现实现一致；删除/重命名/模式变更仍被正确识别。

### X-07（P3，源码确认）符号查询每次 reconcile 全树枚举，查询全量扫描并排序

**位置**：[service.ts](../packages/search/service.ts) 的 `symbols`（约 267 行）在索引 validated 且无构建时调用 `reconcile(false, signal)`（约 629 行），后者执行 `this.inventory()` 全树 `readdir + lstat`；[store.ts](../packages/search/store.ts) 的 `query`（约 319 行）遍历所有文件的所有符号，收集匹配后全量排序，再 `slice`。

**影响**：每次带 `query` 的 `repo_map` 都会先走一遍工作区；本仓库因 X-03 的 29,581 个文件达到约 5 s。即使忽略集修好，10,000 文件的仓库每次查询仍有约 100–300 ms 的枚举成本；`query` 的全量扫描/排序则随符号数增长。

**建议**：

- 给 `reconcile` 加一个短 TTL 或“文件工具写入的 dirty 集合为空时跳过全树枚举”，并保留显式刷新/定时校验；新鲜度仍要在结果里如实报告。
- `SourceIndex` 增加按名字前缀/子串的索引（它已经是内存结构，可按首字符或小写名建 `Map<string, SymbolRecord[]>`），分页在索引层完成，避免每次 `MAX_SAFE_INTEGER` 全量取回再 `slice`。
- 游标续页时只取需要的窗口，不要先物化全部符号。

**验收**：连续两次相同 `repo_map` 查询的第二次不触发全树 `lstat`（或有明确 TTL 证据）；100k 符号的夹具中单页查询时间不随总符号数线性增长；索引变更后游标仍能正确失效。

### X-08（P3，已实测）`repoMapContext` 每轮同步扫树，阻塞 Host 事件循环

**位置**：[repo-map.ts](../packages/tools/repo-map.ts) 的 `scanRepoFiles`（约 256 行）使用 `readdirSync`/`lstatSync`；`repoMapContext`（约 373 行）在 [run-snapshots.ts](../packages/core/run-snapshots.ts) 约 140 行被调用。

**实测**：首次 435 ms，缓存命中后的“只校验元数据”仍需 37 ms（并行测试负载下 117 ms）。这是一次运行开始时的一次性成本，但它是同步的，期间 Host 不能转发流、不能处理其他会话的请求。

**建议**：改成 `fs/promises` 版本；把缓存校验的节奏降到“每次运行一次”之外（例如 2 s 内的重复调用直接复用），或在文件工具/工作区写入时标记 dirty、只在 dirty 时重扫。`run-snapshots` 的调用点本身是异步函数，改动不需要改调用约定。

**验收**：无变化的连续两次 `repoMapContext` 不产生同步目录遍历；Host 在调用期间仍能处理一条并发的 `host.info`（用计时夹具证明事件循环未被阻塞超过 10 ms）；`YUANTU_REPO_MAP=off` 行为不变。

### X-09（P3，源码确认）中文界面下 i18n 观察器仍遍历每个新增子树

**位置**：[i18n.ts](../apps/desktop/i18n.ts) 的 `translateDocument`（约 1271 行）与 `MutationObserver`（约 1318 行）。观察器无条件对每个 `addedNodes` 调用 `translateDocument`；后者即使 `language === 'zh-CN'`（`translatedText` 直接返回原文）也仍会：

- 用 `TreeWalker` 收集子树的所有文本节点；
- 用 `querySelectorAll('*')` 收集所有元素；
- 逐个元素检查 `closest(excludedContent)` 并要求三个翻译属性。

`language` 默认是 `zh-CN`，`setLocale` 在设置加载时就会安装观察器。

**影响**：中文是源语言，却要为每次流式消息块、每个面板重绘付出一次 DOM 遍历；在长回答/大量工具卡片时，这部分工作与渲染本身同量级。由于 `translatedText` 在中文下不改文本，观察器不会自触发，但收集与属性检查仍然发生。

**建议**：在观察器回调开头对 `zh-CN` 直接返回（源文本已经是中文）；`setLocale` 切换语言时仍执行完整的 `translateDocument(document)`，以保证从英文切回中文能恢复原文。这样默认语言路径零额外遍历，切换语言路径不变。

**验收**：中文下新增一个 10,000 节点子树，观察器不产生 `TreeWalker`/`querySelectorAll` 调用（可用计数桩或性能断言）；切到 `en-US` 后所有既有节点仍被翻译；切回中文后文本恢复；`desktop-i18n` 与桌面冒烟通过。

### X-10（P3，已实测）`protocol/index.ts` 单 barrel 被 222 个文件引用

## 8. 建议顺序

1. **X-01 挂起**：先修 `openBlobBatch` 的失败路径，并加回归。它是唯一会让运行“永远不结束”的缺陷，优先级高于所有性能项。
2. **X-02 忽略规则**：在仓库初始化时写 `.git/info/exclude`，并把 `MAX_FILES` 检查移到 runtime 过滤之后。改动小，直接消除“运行态进入版本库”和“快照把冻结撑爆”的两个风险。
3. **X-03 枚举真源**：Git 工作树改用 `git ls-files`，统一 `repo_map`/索引/`list_files` 的忽略策略。它同时改善搜索质量、符号索引完整性和每次 `repo_map` 的 5 s 枚举。
4. **X-04 快照回收**：先做引用计数 + 保留期清理，再做仓库级内容寻址去重。
5. **X-05 / X-06 冻结与导出**：冻结并行读/暂存；导出按基线差异缩小范围。每一步都用 `benchmarks/worktree-fill.ts` 的同机对照。
6. **X-07 至 X-09**：索引 TTL/内存索引、`repoMapContext` 异步化、i18n 中文短路。都是低风险、可独立验证的改动。
7. **X-11 至 X-13**：测试资源分组、数据库整理入口、包体清理。放在功能项之后。

## 9. 扫描限制

- 本轮没有做真窗口桌面交互录制（输入延迟、长回答绘制、滚动），也没有真实模型端到端任务；X-09 与 R-06 的交互影响仍只有源码证据。
