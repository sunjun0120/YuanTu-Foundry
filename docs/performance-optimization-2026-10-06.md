## 统计字段的使用边界

`firstTokenMs` 仍按回答步骤累计，只有真正发出的 `message.delta` 正文能设置该步骤的首字时刻。它包含正文出现前的摘要和请求等待，但内部摘要正文不能充当可见首字。多步骤场景不能把这个累计量直接当作整轮的首次正文时间。

`decodeKnown === true` 才能展示正文 token/秒。只有纯正文响应、无工具调用或工具参数输出，并且 Provider 报告有效的推理 token 拆分时，才记录 `outputTokens - reasoningTokens`；未知、无效拆分和旧统计混合均保守显示未知。这是流事件区间的商值，短流或服务端缓冲下不代表服务端真实生成速度。

`statistics.requestTiming` 是独立、可加总的计量：

| 字段                            | 语义                                                     |
| ------------------------------- | -------------------------------------------------------- |
| `requests` / `providerMs`       | 所有实际 Provider 调用的次数与耗时，包括摘要、失败和取消 |
| `summaryRequests` / `summaryMs` | 上述集合中的摘要请求                                     |
| `failedRequests` / `failedMs`   | 上述集合中以异常结束的请求；正常返回 `length` 不算异常   |
| `retryWaitMs`                   | 已实际发生的退避等待，取消时只记录已等待部分             |
| `lengthCount`                   | 正常响应中 `finish_reason=length` 的次数                 |

`summaryMs` 和 `failedMs` 是 `providerMs` 的子集，可能相互重叠，不能把三项相加当成总时间。旧 `modelMs` 继续只结算已完成回答步骤；`modelMs=0` 不代表没有请求。新增 `provider.request.finished` 保存每次调用的目的、起止、耗时及结束类型。

成功提交的摘要用量已包含在本次运行统计中，`run.finished.compactionUsage` 标记这部分用量；会话重建先保留 `context.compacted` 的用量，再从运行增量中扣除重复项。未提交的摘要仍计入运行，独立压缩与运行结束前的已提交用量仍可查询。没有该标记的旧日志保持原有折叠语义，不猜测历史事件归属。

新压缩事件持久化 `runId`，内部统计投影持久化尚未确认的摘要时间来源；对应运行结束且四项摘要用量匹配后，才能解除这一个来源的未知标记。独立压缩、标题请求、旧运行、用量不匹配或中断的来源继续保持未知。公开的统计、单投影读取和会话快照不暴露内部元数据；投影身份改变后旧派生检查点自动重新折叠，不修改历史事实。

## 摘要与工具行为

摘要批次选择先要求至少 `min(1024, 配置的摘要输出上限)` 的输出空间。新的指令保留原有八部分和约束，字符数从 1954 缩到 1316。截断后从完整对话切点选取较小、在最新校准下仍可发送的批次；每次上下文准备最多重试一次，所有批次共享摘要超时。只有全部摘要完成并通过约束检查才提交新历史，失败或超时保留原始历史；最终限制信息包含截断原因、输出和推理 token、工具调用情况。

`tool.started` 继续表示工具组接收，不改协议结果顺序。新增 `tool.execution.started` / `tool.execution.finished` 表示通过守卫和审批后，每次真正执行工具正文的区间。`tool.finished.timing` 包含排队、调度管线区间、实际执行累计耗时、尝试次数及完整性。观察者同步抛错或异步拒绝不改变工具结果，也不触发重复执行。

并发值明确标记 `scope: model-tool-batch`，只覆盖模型顶层工具组，PTC 程序内部调用没有独立纳入这个峰值。超时重试可能与尚未停止的前一次尝试重叠，此时返回结果标记 `executionComplete: false`；后续实际结束事件记录真实终点，已发出的结果快照保持不变。

## 真实模型复验结果

首次实验共 124 次请求、51 次 Agent 运行：123 次请求返回 HTTP 200，一次未取得响应的请求达到 90 秒超时；50 次运行完成、1 次失败。超时位于工具并发对照的 `tools/1/4`，在尚未执行工具时发生，完整保留为失败样本，不把其零输入用量解释成没有远端消耗。第二次最终版本摘要复验另有 6 次 HTTP 200 请求、2 次完成运行。

原始 JSONL 的调用次数、摘要次数、异常次数、截断次数、请求时间及四项用量均通过独立汇总断言；所有已完成运行的重建用量和分项请求时间与运行结果一致。首次四个摘要场景均正确保留最早的验证信息；其中一个合法窗口场景发生 `length`，仅一次较小批次重试后完成，整轮首次正文时间与步骤首字累计值相差 24.4–29.7 毫秒。第二次小窗口与合法窗口均完成，差值为 42.8 / 24.4 毫秒；四项用量、时间字段和完整性标记均与重建结果一致，并通过另开 `SessionStore` 读取持久化检查点复验。

上述差值的两个起算点不同，包含运行入口到步骤开始的准备时间，不能直接称为同起点计时误差。按持久化 `step.started` 对齐正文事件的本地回归另行验证；真实摘要场景的入口级差值表明内部摘要正文没有再次提前十几秒冒充可见首字。

并发对照的五次成功运行中，实际执行事件与受控工具正文的起止偏差最大为 2.3 毫秒；配额 1 的真实峰值为 1，配额 4 的真实峰值为 3。一次超时运行没有进入工具正文，单独报告；这组样本不证明整轮延迟普遍下降。

native/PTC 实验每次恢复错误的合成加法模块，要求读取、编辑并执行相同 Node 校验，保留这些步骤所需的工具及审批规则。20 次运行均完成，文件结果和实际命令的成功输出均验证。PTC 的累计输入 token 中位数减少 56.0%，但请求数中位数没有下降，工具耗时中位数从 0.137 增到 1.285 秒；逐对墙钟差值中位数为 +4.565 秒，范围 -66.245 至 +47.904 秒。PTC 的调用路径和程序启动成本同时变化，不能把结果只归因于目录大小。
