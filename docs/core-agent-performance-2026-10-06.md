# 核心 Agent 真实模型性能深测（2026-10-06）

## 结论

在提交 `809cc7f` 的核心 Agent 上，使用用户指定的 `DeepSeek-V4.1-Flash` 和 API 服务做了 69 次真实请求。所有请求均返回 HTTP 200；31 次真实 Agent 运行中，27 次完成、4 次因上下文预算限制结束。另有 24 次本地响应回放，全部完成。本次只增加测试证据和报告，没有修改生产逻辑。

当前最明确的问题是性能统计口径和摘要输出预算。内部摘要会污染用户可见首字时间，推理 token 会被计入仅从正文开始计算的解码速度，小窗口压缩又可能把摘要输出预算缩到 77 token。工具调度本身按并发配额执行，但工具事件无法准确表示每个工具的实际起止时间。

在本次短回复、受控工具与合成历史样本中，主要等待发生在远端请求。本地循环、SQLite 和上下文缓存没有呈现需要优先重写的性能瓶颈。这个结论不覆盖长输出、小时级任务、多会话竞争或所有工具类别。

## 实验方法与证据

- 服务地址为 `https://llmapi.isrc.ac.cn/v1`，模型 ID 为 `DeepSeek-V4.1-Flash`。密钥只通过关闭回显的终端输入进入测试进程，没有写入配置、脚本、报告或请求日志。
- 69 次真实请求中，49 次来自真实 Agent 路径，20 次为直接 Provider 对照。使用实际 `Agent`、`OpenAIProvider`、`SessionStore`、工具注册及调度路径；24 次本地回放复用了已获得的模型响应，不计作真实 API 请求。
- 请求最长允许 90 秒，单场景 Agent 最长允许 120 秒、最多 5 次模型请求。常规短回复及工具实验输出上限为 512 token，后续完整任务及压缩对照为 1024 token。没有遭遇 HTTP 错误；单次请求最长实测 46.435 秒。
- 目录和历史对照各 6 对、推理参数对照 4 对、工具调度对照 3 对、完整任务对照 2 对；使用交替 AB/BA 顺序。目录每种配置的请求 SHA256 在组内一致。样本较小且缓存状态不完全相同，不能据此宣称稳定的服务延迟提升。
- 历史和文件内容均为合成数据。完整任务要求读取合成模块、将错误的减法修复为加法，并实际执行 Node 校验；每次独立恢复初始文件。
- 原始脱敏事件在 `.scratch/core-performance-20261006/measurements.jsonl`，全量汇总在 `.scratch/core-performance-20261006/analysis.json`，本地基准日志在 `.scratch/core-performance-20261006/baseline-bench.log`。这些证据和测试、分析脚本保留在本地，不随 Git 提交；当前测试脚本是后续对照版本，重跑早期实验需恢复其 512 token 输出上限。运行器生成的 `summary.json` 只包含最后一个进程的局部结果，不能作为全量统计依据，已清理。

| --------------------- | -----: | ----------------: | -------------: | --------------: |
| 完整工具目录          |      6 |             11712 |       8.296 秒 | 1.571—17.464 秒 |
| 最小读取工具目录      |      6 |              2693 |       3.793 秒 | 1.439—23.240 秒 |
| 短历史                |      6 |             11712 |       3.310 秒 |  1.481—7.232 秒 |

完整 Agent 实际发送 68 个工具；最小目录在实际读取工具和运行时工具组合后发送 9 个。最小目录稳定减少 9019 个输入 token，即约 77.0%。但是逐对比较只有 3/6 更快，差值跨度很大；完整目录缓存命中占输入 token 的约 99.45%，最小目录约 83.18%。输入减少是可靠事实，固定延迟或费用降幅尚未证明，也不能为减少目录而删除任务必要的能力。

长历史增加 4448 个输入 token，却有 4/6 配对请求更快，说明这些短请求不能可靠估计输入长度与服务延迟的关系。`low` 仅有 2/4 更快，没有证明能稳定减少推理或延迟；不传参数不等于关闭推理，HTTP 200 也不能单独证明参数的具体执行语义。

12 次目录对照的 Provider 请求累计时间占 Agent 累计墙钟时间约 99.64%。扣除请求的本地余量中位数为 31.36 毫秒，范围 25.17—38.02 毫秒。这是当前短回复实验的耗时分解，不应推广到高频工具、长输出和并发会话。

## 工具调度与完整任务

工具实验由真实模型一次提出三个读取调用，实际工具延迟分别设为 900、200、200 毫秒，均通过安全并行分类。每种配额重复 3 次；耗时按实际工具执行时间区间的并集计算。

| 并发配额 | 实际并行峰值 | 工具阶段耗时中位数 |
| -------- | -----------: | -----------------: |
| 1        |            1 |       1318.28 毫秒 |
| 4        |            3 |        900.31 毫秒 |

并行将这个受控工具阶段缩短约 31.7%，`statistics.toolMs` 与实际工具区间并集接近，调度配额真实生效。但一次并行场景的整轮耗时达到 48.55 秒，其中单次模型请求耗时 46.43 秒；工具阶段节省不能等同于整轮稳定加速。

完整任务比较 native 与程序化工具调用（PTC）两种工具目录模式。两种模式各完成两次，四次均真实修复文件并执行校验成功。native 第一次使用 `read_file`、`read_file`、`edit_file`、`run_command`，第二次自选 `run_code` 批量读取，再调用 `edit_file`、`run_command`；PTC 两次均通过两次 `run_code` 完成读取以及修改后校验。因此这是目录模式对照，实际调用路径没有严格隔离成“完全原生”与“完全程序化”。

| 路径            | 两次任务请求数 | 两次累计输入 token | 两次任务墙钟耗时 |
| --------------- | -------------- | ------------------ | ---------------- |
| native 目录模式 | 4、4           | 14763、14833       | 11.07、38.10 秒  |
| PTC 目录模式    | 3、3           | 4976、4748         | 47.55、24.93 秒  |

本次 PTC 模式样本比 native 模式少 25% 的模型请求数和约 67.1% 的累计输入 token，但工具阶段包含更多程序进程启动，整轮没有稳定胜出。由于只有两对样本且实际调用路径不同，不能将差异全部归因于目录模式；它支持继续评估批处理减少往返的潜力，不支持全局默认切换。

`packages/core/agent.ts:3380` 在整个工具组进入调度前发送全部 `tool.started`，`:3421` 在整组完成后按模型调用顺序发送 `tool.finished`。因此配额为 1 时也能看到三个工具同时“开始”，快速工具的完成通知会被慢工具延后。建议保留结果协议顺序，额外区分排队、实际执行起止及单工具耗时；不能从当前事件推导真实并发峰值，也不应据此判定调度未生效。

## 已复现的问题与优化机会

### 1. 摘要输出预算可能过小，且限制原因不够明确

将测试上下文窗口显式设为 10000 token，保留较长合成历史，先做三个重复场景，再做一个明确请求预算对照。四次输出均为 77 token，全部用于推理，正文为空，`finish_reason=length`。后续对照的目标输出上限明确设为 1024，并增加请求体元数据记录，直接确认实际摘要请求的 `max_completion_tokens=77`。四次实际请求体的 SHA256 全部相同（`fce8000320176355facbcfdb4c015072a9b6172feed4000a928b66bc60203780`），均为 29073 字节、55 条消息，因此也支持前三次发送上限为 77。前三次没有单独保留 Agent 目标上限，不能从最终请求体反推该配置。四次 Agent 最终为 `limited`，不是网络失败。

这属于人为配置的小窗口压力测试，10000 不代表模型真实容量。`packages/core/compaction-policy.ts:24` 默认固定 65536 token 压缩预留量，使 10000 和 32000 的主动压缩策略不合法，运行转入反应式上下文保护；32000 对照直接完成，没有实际摘要，不构成摘要成功证据。

原因链在 `packages/core/context.ts:449` 的 64 token 最低摘要输出量、`:472` 的容纳判断、`:773` 的贪心扩展批次以及 `:814` 的最终预算传递。可以装入摘要输入的批次，不一定还能留下足够的推理和有效摘要输出。预算估计还偏保守：77 token 场景实际服务端输入为 6326 token，不能将估计值当作实测输入。

另用合法的 100000 token 窗口和 20000 token 压缩阈值测试两次。摘要均获得 1024 输出预算：一次输出触顶，被安全丢弃，主请求仍完成；另一次以 657 输出 token 正常结束并触发 `context.compacted`，主请求也完成。因此简单提高到 1024 仍不能保证当前摘要指令完成。

建议为可用摘要和推理保留输出预算，用这个约束控制摘要批次大小；缩短摘要目标，遇到截断时在明确的时间、调用和费用上限内缩小批次重试，并保留原始历史。应在最终限制原因中保留摘要失败详情。当前丢弃截断摘要、保留历史的保护有效，但“当前用户请求超出上下文预算”的通用提示不足以解释本次失败。

### 2. 推理 token 与可见解码时间混用，界面速度被放大

预检真实请求返回 64 个输出 token，其中 60 个为推理、4 个为非推理输出。Agent 的 `decodeTokens` 为 64，`decodeMs` 仅为正文开始后的 8.19 毫秒。界面公式得到约 7812 tok/s；同一时间段只按 4 个非推理 token 计算约为 488 tok/s，分子口径相差 16 倍。短流及服务端缓冲还会进一步影响这类商值，后一个数也不等于真实生成速度。

`packages/core/agent.ts:1034` 累加总输出 token，`:3095` 传入 `response.usage.outputTokens`；`apps/desktop/renderer-statistics.ts:232` 用它除以正文解码时间。建议明确区分总请求耗时、推理、可见正文与工具参数首字及解码时间；Provider 未提供拆分用量时应显示未知，不能伪造精确的正文 token 数。

### 3. 内部摘要污染用户可见首字时间和解码区间

上面的合法压缩策略两次测试均复现：

| 场景                 | Agent 上报 firstTokenMs | 首个实际 message.delta |      提前量 |
| -------------------- | ----------------------: | ---------------------: | ----------: |
| 摘要截断，主请求完成 |                21.07 秒 |               35.85 秒 | 约 14.78 秒 |
| 摘要成功，主请求完成 |                15.04 秒 |               30.69 秒 | 约 15.65 秒 |

这里 `message.delta` 从本次运行入口计时，上报字段从步骤起点计时；入口差异只有几十毫秒，不足以解释上述十几秒偏差。原始请求回调和事件时间均保留，支持将偏差定位到摘要。

`packages/core/agent.ts:989` 的 measured Provider 钩子对任何正文设置步骤首字时间，`:2486` 将这个 Provider 传入摘要器；`packages/core/context.ts:816` 的空 `onText` 不会阻止外层测量钩子记录内部摘要正文。主请求最终结算又复用这个首字时间，导致 `decodeMs` 把摘要尾部和下一次主请求等待算进去。

建议把内部摘要请求与主回答的时间状态分开。用户可见首字应由真正面向用户的流事件记录；若统计意图是多步骤累计，则应明确字段名称，并保留独立的首次可见正文指标。回归场景必须同时覆盖摘要成功和截断后回退。

### 4. 未形成回答的请求等待在旧 modelMs 中不可见

四个小窗口限制场景真实请求耗时约 1.65—25.66 秒，服务端有输出用量，而 `statistics.modelMs` 为 0。源码已明确约定没有形成完整回答的步骤不提交该时间段，这不是违反既有字段契约的实现错误；问题是目前单看这个字段会漏掉实际等待和消耗。

建议在兼容现有字段的基础上，增加独立 Provider 请求、摘要、失败及退避等待时间。将请求耗时与完整回答统计分开，避免把 `modelMs=0` 理解成没有调用模型。

## 建议推进顺序

| 优先级 | 工作                                             | 验证标准                                                                      |
| ------ | ------------------------------------------------ | ----------------------------------------------------------------------------- |
| P1     | 修复首字、解码速度口径并补充分项请求时间         | 真实 reasoning 响应、摘要成功与回退、工具参数流均对齐原始事件；不伪造未知用量 |
| P1     | 让摘要预算能够产出有效正文，保留具体失败原因     | 小窗口用例不再被贪心批次压至不可用预算；截断不丢历史；重试有明确上限          |
| P2     | 为工具增加实际执行起止和排队状态                 | 配额 1/4、快慢混合工具下，事件与实际执行时间吻合，结果顺序保持正确            |
| P2     | 按任务阶段缩减目录，针对批处理任务选择 PTC       | 保留任务所需能力、权限和审批；统计 token、请求数与实际完成效果，扩大配对样本  |
| 后续   | 长输出、小时级任务、多会话竞争和更多工具故障测试 | 独立记录 P50/P95、资源用量及失败恢复；本次样本不能替代这些测试                |
